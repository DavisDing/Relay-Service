## 1. 目标、现状与差异

### 1.1 当前相关实现

本仓库只有文档和协作配置，没有服务端、Web、Mac 源码、接口、数据库、Compose 或测试工程；核实依据见 AI_CONTEXT 1～4。

REQUIREMENT 保存用户 NAS/配置输入的历史摘要，以及对独立 Mac 工程的历史核对记录。本轮只读查阅了官方资料和旧 Mac 公开源码，见第 13 节；当前 NAS 接口、依赖版本、完整旧数据 schema 与受保护 UI 尚未实机验证，不将资料核对写成集成成功。

### 1.2 已确认的设计输入（引用，不新增确认）

- Mac Relay → NAS Relay → 既有 LiteLLM；外部推理客户端可继续直接调用 LiteLLM。Relay 不要求承载所有推理流量，不建立第二套网关 Key/扣费引擎（FR-K02/FR-D01、3.1/3.2）。
- NAS Web 做管理，Mac 做连接、监控、缓存和通知；浏览器/Mac 不持有网关管理 Key（FR-K01/FR-K04/FR-C03）。
- 首期不是只读版：包含监控、Key/模型管理、定时能力/质量探针、告警、Mac 连接/自动更新和旧数据替换迁移（第 11 节）。
- LiteLLM/workbuddy2api 与独立供应商余额为当前范围；Ollama 暂缓，既有 Open WebUI 直连路径不擅改（FR-D01/FR-P04）。
- 质量异常仅告警；探针须显式启用，受已确认周期/预算/并发保护；不安全或未定价对象不能盲测（FR-P03/FR-P04/FR-A01）。
- NAS 为远程账本事实源；旧 Mac 迁移核验/恢复成功后才清理本地清单数据；云副本/秘密分别处理（FR-D03/FR-C04）。

### 1.3 不得掩盖的差异

| 目标 | 当前输入/风险 | 处理方式 |
|---|---|---|
| 原生虚拟 Key、日志与管理 | 历史输入称现有 LiteLLM 无数据库，文件配置只读；接口/许可未实测 | E-02 形成矩阵后提出数据库/日志/模型迁移方案；未实施兼容性降级不算完整验收，D-02 决定产品取舍 |
| 请求/回答正文查看 | 统计接口是否包含正文、日志接入方式未知 | D-04 先限定内容/范围；T-03 验证接入，不默认所有请求改道 Relay |
| 自动安装更新 | 历史记录中的旧更新能力是检查/下载，不是完整安装流程 | E-06 核实身份/签名资源，D-09 确认更新控制；T-07 出安全设计 |
| 多实例/多设备与 Top 5 | 使用者权限/已读共享、稳定别名、逻辑请求证据仍未完整定义 | D-01 和 T-03/T-06 先冻结口径；不把不同名称猜成同模型或用缺失请求编造排名 |

## 2. 方案边界与设计责任

### 2.1 逻辑职责（需求边界，不预设部署/代码分层）

| 部分 | 需要设计的能力 | 禁止隐含扩展 |
|---|---|---|
| 既有 LiteLLM | 版本/权限识别、目录与部署、请求账本、原生调用 Key、模型/路由接口 | 不擅自重建、升级、改路由或复制第二套预算引擎 |
| NAS Relay | 归一采集、历史/覆盖、余额适配、探针与预算、告警、鉴权/设备、迁移导入、审计 | 不默认挂 Docker socket；不保证所有上游有同等接口 |
| NAS Web | 接入/管理、探针启用与策略、数据/保留查看、授权、风险预览 | 不向浏览器下发上游/管理秘密；未定页面不当作已确认 UI |
| Mac Relay | 配对/撤销、快照展示、详情同步、离线缓存、通知、迁移向导、自动更新 | 不直连上游、不管理 NAS 配置、不继续写本地/iCloud 事实账本 |

上述职责不意味着四个新容器或固定微服务架构。后端/Web 技术栈、存储、复用实现和新增依赖由 T-01 提出，并说明名称、固定版本、用途、许可证、必要性及维护影响。

### 2.2 推荐选型与待冻结内容

- 推荐：Python/FastAPI 模块化单体、React/TypeScript 静态 Web、PostgreSQL、现有 SwiftUI/AppKit Mac；通过 HTTP 适配既有 LiteLLM，采集和探针任务由数据库保存状态，详见 10.6。
- LiteLLM 与 Relay 使用独立数据库/账号，同一 PostgreSQL 实例可承载两库；应用不跨库直接读写私有表。版本兼容与资源占用需 M0 核实。
- 运行时大版本基线、依赖用途和选型理由已给建议，具体补丁版本、镜像摘要、许可证和锁文件待验证后冻结；本轮没有安装软件或新增业务依赖。
- Sparkle 为更新候选；评测优先客观断言，是否使用其他评测工具由实际需求决定。秘密保护与备份恢复方案仍按 T-02/T-07 展开。
- T-01～T-07 仍不是已批准详细设计；D 项中的用户/正文/迁移等产品取舍未因技术栈推荐而得到确认。

## 3. 接口与集成准备

### 3.1 边界清单（接口合同待设计）

| 边界 | 需求来源 | 实施前要确定的合同/证据 |
|---|---|---|
| Web ↔ NAS Relay | FR-K04/FR-W01 | 初始化/登录/会话，管理操作、二次确认、审计；只读/写入/高风险权限逐项校验 |
| Mac ↔ NAS Relay | FR-C01/FR-C02/FR-A01 | 一次性配对、可撤销设备凭据、数据版本/快照、增量告警、断线和兼容错误 |

### 3.2 兼容性验证输出

针对每个外部端点记录：安装版本/摘要、来源、实际路径/方法、所需权限、响应字段、是否触发真实推理/写入、计费可能性、许可限制、测试时间及通过/失败/未执行。

只读首次接入应验证不触发模型推理。健康端点、数据库日志和 YAML/API 可写能力不能仅靠名称推断。无权限、未支持、未配置、未验证单独呈现；实际余额认证由 E-03 核实。

## 4. 数据、兼容与生命周期准备

### 4.1 待定义的数据边界（非已选 schema）

- 实例/渠道/账户/凭据引用/稳定部署/对外别名分离，支持多实例，同名不同渠道不合并。
- 账本区分请求、尝试和逻辑调用；来源标识、采集游标、覆盖区间、源时间/采集时间与价格来源可追溯。
- 探针保存计划/当轮入选、测试/基线版本、执行状态、预算预留/对账、证据和有效样本；永久告警与证据保留分离。
- 设备/管理员/会话、审计与秘密存储边界由 T-02 定义，不将秘密存入普通导出/日志或设备快照。
- 迁移保存批次/来源/阶段、幂等标识、冲突/核对结果与明确清理清单；不是上传整个旧应用目录。

### 4.2 生命周期约束

已确认：元数据默认 180 天，日/月聚合 2 年；正文默认关闭、开启后 7 天；探针证据默认 90 天；告警默认不自动过期。各项可配置，缩短/清理须预览并确认（FR-D04）。

D-04 仍需限定正文范围；D-10 仍需明确备份正文/秘密边界、删除承诺和恢复目标。禁止声称删除在线数据已经同步删除所有备份。恢复时已过期正文不能重新暴露。

### 4.3 迁移与回滚责任

- 旧数据 schema、秘密和 iCloud 状态先 E-06 核实，再给字段/冲突清单；D-08 决定冲突及云清理取舍。
- 不以初始化清空 NAS 数据；未解决冲突、部分导入、中断或读回/恢复验证失败均不能进入本地清理。
- 数据库/模型管理迁移和应用替换各自说明备份、兼容、失败恢复及不可逆步骤。降级镜像/应用不自动回滚数据格式。
- 当前未执行数据变更、备份、导入、清理或回滚；不存在可声称已验证的迁移脚本。

## 5. 页面与交互准备

- Web 信息架构沿用需求 3.2 的连接/模型、访问管理、监控策略、系统区域，不在本轮确定页面视觉或新增设计稿。
- 接入支持矩阵、保存范围与覆盖、价格/汇率来源、探针费用/可覆盖预览、管理变更摘要是需要展示的信息，不等于已确认组件布局。
- 各数据视图区分加载、空、真实零、未知/无权限/未支持、失败旧缓存、过期、部分成功、待核对和删除，不以统一“0/绿色”掩盖差异。
- Mac 复用前读取旧工程自己的 AGENTS/UI 保护范围。设备连接、正文默认权限、迁移向导等必要变化先说明影响；当前无 UI 修改授权例外。
- D-05 明确刷新目标，T-06 定义一致数据版本和详情更新。D-01 明确多设备/已读范围，离线通知合并不得丢掉服务端历史。
- Mock 只能辅助离线验证与 UI 开发，标识清楚，不冒充真实余额、模型可用性、费用或上线验收。

## 9. 可行性评审结论（2026-10-08）

**总体有条件可行，可以继续详细设计；尚不具备完整首期实施和验收的全部前提。** 常规 Web/Mac 展示、采集、权限与调度没有发现结构性障碍。主要约束集中在既有 LiteLLM 的持久化/管理模式、日志可得性、预算内测试覆盖，以及旧应用迁移/发布。当前未做 NAS 容量或接口实测，不据 N5105/16GB 单独保证性能，不给缺少人员与验证依据的工期。

### 9.1 按功能判断

| 功能及需求 | 判断 | 实施前提与实际工作 |
|---|---|---|
| 网关目录/状态、Web/Mac 摘要（FR-M01/FR-C01/FR-C02） | 可设计实施；安装版本适配待验证 | LiteLLM 适配器、稳定部署映射、支持矩阵、采集状态/缓存、版本化展示 API；公开别名不当作唯一部署 |
| 原生虚拟 Key/预算（FR-K02） | 有条件可行；现有无数据库输入不满足 | 官方配置要求 PostgreSQL，见 S-01；先完成数据库接入，再验证创建/限制/撤销及请求归属。Relay 不自行仿造网关 Key |
| 模型/路由写管理（FR-M02/FR-K04） | 有条件可行；只读 YAML 不能直接完成 | 文件来源模型需迁到可管理来源或保留指引，见 S-02；模型 CRUD 可行不等于全部 router/fallback 参数均可热更新，需逐项验证 |
| 请求统计/历史/Top 5（FR-D01/FR-D03/FR-P04） | 新数据可行；未记录的历史不可恢复 | 实际启用日志、分页采集和稳定归属；旧聚合可迁移，但无法补出请求级证据。日志截断/计数上限需要实测，见 S-03 |
| 请求/回答正文（FR-D04） | 扩展路径可行；完整性尚有条件 | 优先评估官方自定义回调扩展；现成 `generic_api` 方案有企业许可门槛，见 S-04。需验证成功/失败/流式中断的字段、来源端过滤、离线丢失和保留策略 |
| Pipio/DeepSeek/workbuddy2api 余额或统计（FR-D02） | 按连接器分别验证 | DeepSeek 有官方余额接口；Pipio 可参考旧解析代码；workbuddy2api 实际版本/接口未知。余额、额度、账单和网关消费各自保留来源，见 S-06/S-07 |
| 可用性/能力/质量（FR-P01～P04） | 有预算约束的检测可行 | 计划、成本预留、模式适配、版本化用例/基线与公平调度；“全部按期测完”和“精确认出换模型”不能据此承诺 |
| Hermes/多媒体探针（FR-P04） | 安全/模式核实前保持跳过 | Hermes API 具备工具调用能力，不能作为普通无副作用补全来测，见 S-08；其他模式按明确的测试适配器接入 |
| 远程鉴权/配对/告警（FR-K04/FR-A01/FR-C01） | 可设计实施 | Web 会话、设备独立凭据、一次性配对、撤销、通知游标、TLS/代理适配；NAS 整体停机时 Web 无法留存新事件、离线 Mac 无法实时通知 |
| 旧 Mac 迁移与安全更新（FR-C03/FR-C04） | 可行但需独立交付工作包 | 旧 UI/JSON/适配器可局部复用；迁移、受控清理、设备 API 与自动安装更新需新实现。现有下载更新能力不足以验收，见 S-07/S-09 |

### 9.2 预算、调度和告警时效的量化约束

以下根据现有需求做算术推导，不是模型报价或 NAS 压测。实际目标数按去重后的、安全可测的部署计算，80 仅使用历史别名数量作示例。

- **调用量**：80 个目标 × 每日 48 轮 = 3,840 次可用性起始调用/日。若 1 USD 全用于这些调用，平均单次必须不超过约 **0.0002604 USD**；能力/质量、重试、裁判和其他费用还会进一步压缩该额度。
- **质量采样**：采用尚未确认的“10 个用例 × 每例 3 次”时，Top 5 每个模型一个部署就需要 150 次调用/轮；每模型两个部署则为 300 次。首次基线另需采样，不能把基线费用排除在日预算之外。
- **串行容量**：并发 1、80 个目标在 30 分钟内完成，单个目标平均总占用须低于 **22.5 秒**，且这还没给其他主动测试留时间。慢响应/超时会使轮次逾期；禁止旧轮未结束又无限堆积新轮。
- **可用性告警**：按每 30 分钟一次、连续 3 次失败的提案，持续故障约需 **60～90 分钟**确认；连续 2 次成功恢复约需 **30～60 分钟**。前提是每轮均实际执行，预算暂停或排队会延长时间。
- **质量告警**：按每 24 小时一轮、连续两轮下降的提案，已有基线时约需 **24～48 小时**确认；新基线、样本不足和预算暂停会更久。这些提案不提供实时“降智检测”。
- **容量规划**：元数据估算量 = 日请求数 × 180 天 × 实测单条含索引占用；正文另计日采集量 × 7 天；证据按日探针量 × 90 天；永久告警和备份单独增长。日请求量、单条大小和可用磁盘未知，D-10 的恢复时间目前无法承诺。

实施建议：启用页同时预览费用和执行时长；展示最后检测、下次计划、实际延迟和覆盖。D-07 的“可用性优先”还需限定用量，否则能力/质量可能永远得不到预算，见 11.1。

## 10. 建议实施架构与核心规则（PROPOSED）

本节提供可评审的推荐方案；涉及 D 项的产品选择仍待确认。没有将建议回写为已确认需求。

### 10.1 部署与数据流

推荐首期使用 **一个 Relay 应用服务承载 API、编译后的 Web 静态文件、采集与调度**，配合持久化存储。Web 与 API 同源，Mac 经 Lucky HTTPS 访问同一 API。请求采集、供应商读取、管理和主动探针分别限流，付费探针并发 1 不应阻塞登录或界面查询。

在 D-02 选择完整原生 Key 管理的前提下，推荐一个受支持的 PostgreSQL 实例，分别建立 LiteLLM 与 Relay 的独立数据库/账号；已有可用实例则优先复用。Relay 经验证的接口采集网关数据，不依赖直接读写 LiteLLM 私有表。两库分别迁移、备份并记录恢复顺序，共享实例的故障影响需要纳入恢复验证。相比再为 Relay 增设一种存储，该方案减少运维种类；版本基线建议见 10.6，实际兼容与 NAS 部署方案尚待验证。

```text
Web / Mac ──HTTPS Lucky──> Relay API ──> Relay 独立数据库
                             │
                             ├─ 采集/管理 ──> LiteLLM ──> LiteLLM 独立数据库
                             ├─ 余额适配 ──> 供应商管理接口
                             └─ 受预算约束的探针 ──> LiteLLM ──> 指定部署

现有推理客户端 ──> LiteLLM ──> 既有上游
可选正文采集：LiteLLM 回调扩展 ──受限异步投递──> Relay 日志入口
```

首期单 Relay 活跃调度实例；任务持久化并使用租约/唯一任务键，避免重启和重复触发。暂不需要 Redis、独立消息集群或专门向量库。推荐的服务语言/Web 框架和运行方式见 10.6；若采用正文扩展，其在 LiteLLM 内运行的薄适配代码独立按网关环境构建和验证，不能强制 LiteLLM 使用 Relay 的 Python 或依赖版本。

### 10.2 模型、Key 与状态的权威来源

- 每个网关是其自身调用 Key、调用预算与路由的权威。Relay 多实例管理使用 `(instance_id, remote_id)` 隔离，同一供应商账户可关联多个实例；账户余额只计一次。
- `model_identity` 是经确认的型号映射，`deployment_id` 是实例内稳定部署，`public_alias` 是调用名称，三者分开。配置摘要、价格和测试版本分别保留；别名变更不抹掉历史。
- Relay 管理写入记录操作 ID、目标及预期版本，状态为 `pending → applied / rejected / indeterminate`。网络超时进入待核对，不因重试重复创建 Key；没有安全的远端核对办法时由管理员处理。
- 外部管理员仍可能直接修改 LiteLLM；目录同步应发现漂移并刷新视图，不能自动把远端覆盖回 Relay 旧配置。冲突写入显示新旧差异。
- YAML 到数据库模型迁移先在验证环境演练导入、名称/部署核对及回滚；正式切换需明确移除旧声明的时点和维护窗口，避免双路由。基础设施仍由指引执行，Relay Web 不获得 NAS 文件写权限。

### 10.3 采集、正文与统计

- 元数据采用分页读取 + 有界时间窗口 + 重叠回查，按源稳定请求/尝试标识幂等合并。游标与数据同事务提交；聚合基于唯一记录更新，修正记录先扣旧贡献再计新值，避免重放累计。
- 页数/总数可能截断或是近似值，不能仅按 `total_pages` 停止采集。对当前版本验证遍历终止方式、排序稳定性和迟到记录回查上限；超过已覆盖窗口的数据缺口明确显示。
- “用户逻辑请求”只能在可信归属、网关请求与内部重试关联可得时计数；不同客户端独立重发默认是不同网关请求，不能仅凭内容相同推断为同一用户意图。Hermes 嵌套调用需关联或分别展示，不重复算作一次端到端费用。
- 正文推荐由来源端明确筛选后异步投递，Relay 入口独立鉴权、限体积、按事件 ID 去重；不照搬将秘密打印到日志的示例。以 `source_request_id` 关联元数据，可先有一方后补齐另一方。
- **交付保证建议**：Relay 不可达时普通推理继续；正文允许出现可见缺口。事件仅在持久化后确认收到，有限重试需有过期时间；若要求断网期间正文也不丢，需设计源端持久缓冲、加密/空间/清理和相应部署变更，再确认 D-04/D-10。官方回调本身不证明可靠重放。
- 保存政策带版本和生效时间，关闭后不得接收队列里过时的新增正文。来源端过滤、Relay 存储、错误日志和备份分别验证；过期正文先在读取时拒绝，再异步清理，不能等清理任务运行才失效。
- 金额使用明确币种/单位的十进制定点表示；网关计费、供应商账单和余额为独立数值。人工价格/汇率更改需新版本，历史重算作为单独标明的估值，不静默改写既有账单或已完成预算日。

### 10.4 调度、质量与告警

- 推荐 1 USD/日及并发 1 以 **一个 Relay 服务所连接的全部实例合计**为作用域，仍需 D-07 确认；新增实例不自动乘出新预算。单独部署的其他 Relay/网关内置健康任务不在此保证内。
- 计划唯一键包含计划、轮次、部署、测试版本；任务冻结范围/参数后进入 `queued → reserved → running → succeeded / failed / uncertain`，未开始任务可为 `paused/skipped`。队列逾期不自动补跑多轮。
- 费用预留和任务领取原子完成；崩溃或调用超时后结果未知的任务不自动再付费执行，先核对且保留可能已产生费用的预留。预算归属按开始日，并明确跨日未结算任务；时间/时区变化不能清零在途支出。
- 先预留达到最低有效样本所需的当轮额度，再启动能力/质量轮次；不足时明确延期。失败样本不作为正常质量不合格直接计分；无法完成的轮次不产生“完整通过”。
- 基线键包含部署、已知上游版本/配置指纹、测试集、评分与参数版本。首次运行建立候选基线，建议管理员确认后启用比较；变化后新建版本。模型真实版本不可见时显示该限制，不声称已锁定供应商内部模型。
- 告警按实例/部署/类型/规则版本关联事件，异常产生、持续更新、恢复分开；已读状态不覆盖事实事件。预算暂停和过期不是恢复成功。无新样本时不累计成功/失败计数。
- 活跃基线超过 90 天证据保留期时，建议原样本到期删除，保留不含正文的版本/评分摘要并标记不可展开原证据；是否允许继续比较或要求重建由 D-07 明确，不能用“基线”绕过保留期。

### 10.5 Mac、授权与迁移

- Web 管理员会话和 Mac 设备凭据分开；配对码短时、单次兑换并限制尝试。设备访问需验证服务实例身份，地址切换到其他 NAS 时重新配对并按服务身份隔离缓存。
- Mac 使用服务端快照版本更新首页/详情，告警使用独立游标；一次采集周期与一次 Mac 读取周期相叠加，端到端时效按“源事件→入库→显示”验证，不能仅测 API 请求耗时。
- **迁移授权例外建议**：普通 Mac 设备 API 保持只读。管理员单独签发绑定设备、NAS、批次、有效期和数据范围的一次性导入授权，只能提交该批次；不能借迁移取得 Key/路由/正文管理权限。关联 D-01/D-08 与 AC-19/26/31，需明确进需求。
- 迁移状态为 `prepared → imported → verified → recovery_verified → cleanup_pending → completed`；存在冲突/秘密未核验/部分提交时保持可恢复状态。已迁移源文件在清理前再次核对摘要，内容变化则停止清理。
- 停写只覆盖当前应用能够控制的进程/同步；其他 Mac 上的旧版或旧副本可能继续向 iCloud 写入。迁移前需列出旧写入者并停止，不承诺新 Mac 能远程停掉所有旧版本。
- 更新推荐评估 Sparkle 2 系列作为候选，固定版本/许可证/打包兼容性在选型时确认；现有 SwiftPM 可执行目标还需验证应用包与 helper 签名。发布更新私钥不随 NAS/客户端分发；供应商凭据存储与发布签名密钥是不同边界。
- 应用代码签名/公证与更新包签名分别验收。D-09 尚未决定公开分发或个人使用路线，不能把 Developer ID 资源未到位等同于技术上完全无法更新，也不能用关闭校验代替安全更新。

### 10.6 明确架构推荐：模块化单体 + 既有网关 + 原生 Mac（PROPOSED）

**推荐组合：Python/FastAPI + React/TypeScript/Vite + PostgreSQL + SwiftUI/AppKit，Docker Compose 部署，Lucky 提供外部 HTTPS。** 选择依据是当前工作以供应商 API 集成、日志采集、统计和低并发评测为主，已有 LiteLLM 承担推理路由、原生 Key 与调用预算；业务量与团队规模均没有证据要求分布式系统。以下是面向本项目的设计判断，不是框架性能排名。

#### 技术栈与版本基线

| 部分 | 推荐 | 作用、必要性与版本边界 |
|---|---|---|
| 服务运行时 | Python 3.14 系列 | 网络采集与评测逻辑采用同一语言，便于维护 Python 日志扩展；这是 Relay 独立运行时，LiteLLM 镜像内部版本不改动。官方列为维护中的版本，实际依赖兼容待验证 |
| API | FastAPI + Uvicorn + Pydantic 2 系列 | 声明请求/响应、验证与 OpenAPI 合同；同一套 API 服务 Web/Mac。FastAPI/Uvicorn 具体版本在兼容验证后锁定 |
| 外部 HTTP | HTTPX AsyncClient | 实例级超时/连接池、流式解析、错误归因；直接访问网关 HTTP API，Relay 不因连接 LiteLLM 就嵌入整套 LiteLLM SDK |
| 持久化 | PostgreSQL 17 系列 | 一个数据库服务内分别建立 `relay`、`litellm` 两个数据库；事务保障采集游标、预算预留和迁移提交。该系列仍受官方支持；目标 LiteLLM 镜像兼容验证是选型前提 |
| 数据访问/迁移 | SQLAlchemy 2 系列 + psycopg 3 系列 + Alembic 1 系列 | 数据访问、异步驱动、版本化 schema 迁移各用一个实现；金额/关联/约束用关系表，来源扩展字段按需 JSONB。每个并发任务独立数据库会话 |
| 管理 Web | React 19 系列 + TypeScript + Vite | 表格/筛选/详情/状态交互；编译成静态文件随 Relay 镜像发布，Node 只用于构建。路由和服务端数据缓存采用 React Router/TanStack Query，版本按 React 兼容组合锁定 |
| Mac | 继续 SwiftUI/AppKit、URLSession、Swift Concurrency | 复用原生菜单栏/详情与交互，通过新 NAS 客户端替换供应商直连；Swift 编译器/SDK 与目标 macOS 27 一起验证。更新候选为 Sparkle 2 系列 |
| 计划和执行 | asyncio + PostgreSQL 任务/租约/预算记录 | 原生周期足够当前分钟/天级计划；任务可靠性由数据库状态承担。无需首期增加 Redis/Celery，不把内存定时器或 FastAPI BackgroundTasks 当持久队列 |
| 部署 | Docker Compose + 现有 Lucky/LiteLLM | 构建静态 Web 和 Python 运行镜像；通常新增 `relay` 与 `postgres` 两个常驻容器，若已有可用 PostgreSQL 则只新增 Relay。NAS 首验 Linux amd64，其他架构另验证 |

这里的大版本是建议兼容基线，未声明已安装、已实测或为最新版本。实施前产出精确锁文件、镜像摘要、许可证和目标架构安装结果；TypeScript/Vite、路由/缓存库等具体版本届时一起固定，避免凭文档填写未经组合验证的补丁号。当前没有批准部署、付费调用或数据迁移。

#### 内部按业务模块组织，统一发布

这些是一个应用内的代码职责，不是六套独立服务；不强制每个模块建立重复的 Controller/Service/DAO 层。

| 模块 | 拥有的业务规则 | 主要边界 |
|---|---|---|
| 访问与设备 | 管理员会话、配对/撤销、操作权限、迁移授权 | Web 与 Mac 权限由服务端校验；管理员会话用安全 Cookie/CSRF 防护，设备使用可撤销的独立令牌 |
| 接入与目录 | 网关支持矩阵、供应商账户、秘密引用、模型/部署映射、管理操作 | 外部调用经过受控适配器；只把脱敏业务对象交给 API |
| 数据采集与查询 | 增量日志、余额快照、聚合/覆盖、正文范围与过期读取 | 采集写入与客户端查询分开；页面读取保存结果，不刷新页面就重新打上游 |
| 探针与评测 | 选模、测试版本/基线、持久任务、费用预留/对账 | 日预算和任务领取同事务；租约丢失/调用结果未知时先核对，不盲目补发付费请求 |
| 告警与通知 | 异常/恢复事件、去重、已读和通知游标 | Web/Mac 从同一事件源读取；普通日志正文不进入告警内容 |
| 迁移与运维 | 导入批次/冲突、完整性/恢复检查、保留清理、审计与版本信息 | 只管理 Relay 自己的数据；LiteLLM 数据库 schema 和 NAS 容器生命周期不由本模块接管 |

拟新增入口为 `server/relay/` 下对应业务包、`web/`、`integrations/litellm/`、`deploy/` 与测试 fixtures；具体文件在实现时创建。Mac 先沿用独立旧工程的受保护 UI 和业务入口；是否合仓由 D-11 决定，不妨碍 API 合同先行设计。

#### 运行、通信和恢复规则

1. **一个应用镜像、首期一个 Uvicorn 进程**：FastAPI lifespan 管理连接池和异步采集/调度循环；Web 请求、采集、探针分别设置连接/并发上限。调度任务异常有明确失败状态和监督恢复，不让循环静默退出。多进程启动会复制生命周期任务，后续扩容前必须拆执行角色或验证单领导者机制。[生命周期依据](https://fastapi.tiangolo.com/advanced/events/)
2. **先持久化再执行**：管理员触发任务先写数据库并返回任务 ID；调度器读取到期任务，短事务领取并预留预算，然后释放数据库锁再请求上游。结束时另一个事务提交结果/费用/告警；探针网络等待期间不占有长事务。租约用于协调执行，不宣称能让外部付费 API 恰好执行一次。
3. **简单 HTTP 合同**：以版本化 REST/JSON API 开始，Web 同源访问，Mac 使用 URLSession。快照带服务身份、数据版本和采集时间；使用条件读取/分页和告警游标，刷新周期采用 D-05 最终值。首期轮询即可满足当前秒/分钟级展示目标；无必要先建 WebSocket。若以后确认更低延迟通知，再增加 SSE，断线仍以数据库事件游标补齐。
4. **有限本地计算**：网络 I/O 异步，重 CPU 的可信评测/大导出需要移出事件循环并限制资源；模型生成代码在 API/调度进程中不执行。若具体测试必须执行生成代码，需单独设计无秘密、受限网络/文件/CPU 的隔离执行环境，不把普通 Python 子进程当安全沙箱。
5. **单库内明确生命周期**：Relay 关系数据、受控文本正文、合成证据先保存于 PostgreSQL 的分离表，分别过滤权限和执行保留策略；大附件不默认入库。预算/任务/游标作为恢复所需状态保存；金额为定点值，不能用浮点累计。LiteLLM 表由 LiteLLM 管理，Relay Alembic 只改 `relay` 库。
6. **故障可解释**：Relay 停止时现有客户端仍可经 LiteLLM 推理；Relay 数据库不可用时管理写入/新付费任务暂停，Mac 显示离线缓存。共用 PostgreSQL 实例故障也可能影响 LiteLLM 鉴权/调用，这属于共享故障域，部署恢复验证需要覆盖，不能承诺绝对互不影响。
7. **部署边界**：复用实际 `ai-network` 时声明为外部网络；数据库不发布宿主端口，Relay 暴露供 Lucky/局域网访问的明确地址。Web 静态资源直接随后端提供，不新增常驻 Node 或 Nginx。数据库持久目录用 NAS 本地卷，不放进 iCloud/同步目录；备份策略与密钥恢复按 D-10/T-02 实施。

该规模下，自建的部分是探针预算、任务状态和业务规则；HTTP、验证、数据库事务和迁移使用成熟组件。FastAPI 的请求后置任务并不代替本方案的持久调度；官方也将重型跨进程任务与轻量后置任务区分，见 [BackgroundTasks](https://fastapi.tiangolo.com/tutorial/background-tasks/)。

#### 取舍与演进触发条件

- 选择 Python 是为了减少当前集成/评测与日志扩展的语言切换；Go/TypeScript 同样可实现服务端，但本项目尚无可复用的该类后端代码，也没有需要通过换语言解决的实测瓶颈。若后续证明运行内存或 CPU 不达标，先定位工作负载再调整，当前不作语言性能承诺。
- 选择 PostgreSQL 是因为完整 LiteLLM Key 管理已引入该前提；Relay 再用 SQLite 会增加第二种存储与备份路径。推荐共用数据库服务、分开数据所有权；数据库主版本升级独立于 Relay 应用发布。
- React 管理 Web 与 Swift 原生 Mac 各自负责最适合的展示；复用 HTTP 合同和测试数据，不为追求同一套 UI 改成 Electron/Tauri，避免重做已有 Mac 体验。
- 先保持一个发布单元；当执行任务持续影响 API 延迟、需要多个 API 副本、或评测计算量明显上升时，**优先把同一代码库/镜像的 worker 独立成进程或容器**，保留 PostgreSQL 任务合同，再评估是否需要消息队列。无需先拆微服务。
- 上游接入通过版本化适配器和固定合同隔离；长期历史查询变慢时先检查索引、按时间分区/归档和聚合，只有实际数据量要求时再评估专用分析库/对象存储。

架构可据此进入接口与数据字典设计。D-02 的网关持久化迁移、D-01 的用户权限、D-04 的正文交付保证、D-07 的预算分配，以及迁移/发布条件仍按需求登记处理；这些不会因推荐框架而自动确定。当前无需修改 AI_CONTEXT 中“无已采用技术栈”的事实。

暂停和静默是不同操作：前者停止启动新的主动测试，后者只控制通知。移除接入和撤销远端调用权限也是不同操作。Web 上应使用具体动作名称与影响预览，而不是一个语义不明的“关闭”按钮。

灾难恢复的权限失效需由受控恢复流程落实，例如重新生成会话/设备授权代际；不能只在恢复后的旧数据库中查“已撤销”字段就认为安全，因为该记录可能不在备份中。管理员恢复入口独立验证身份；最终方案由 T-02/T-07 给出，不要求用户选择令牌算法。该建议以实际执行恢复流程为前提，不承诺识别任意手工复制数据库的行为。
