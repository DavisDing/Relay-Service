## 0. 设计基线与阅读导航

### 0.1 当前结论

推荐一个 NAS Relay 模块化单体（API、静态 Web、采集/调度/告警）与独立 PostgreSQL 数据库，连接用户既有 LiteLLM；Mac、Android 各自为只读设备客户端。LiteLLM 继续拥有原生调用 Key、路由和调用账本，Relay 保存采集副本及自身策略、探针预算、事件与设备授权。

统一运维 Web 的管理对象分三类：Relay 自身配置可由管理员管理；LiteLLM Key/模型/路由属于已确认管理范围，经接口验证和操作确认执行；其余外部服务首期只读接入。容器/数据库/宿主机操作提供指引，镜像更新发现依赖可信只读证据，不能据此获得执行更新权限。

产品范围已按 REQUIREMENT D-01/D-02/D-05～D-13 记录，D-03/D-04 仍为 NEEDS_CONFIRMATION。技术栈、接口路径、数据字典、页面、版本锁定和工作包为 PROPOSED；当前没有业务源码、运行服务或业务验收结果。整理文档不改变这些状态。

### 1.2 已确认的设计输入（引用，不新增确认）

- Mac Relay → NAS Relay → 既有 LiteLLM；外部推理客户端可继续直接调用 LiteLLM。Relay 不要求承载所有推理流量，不建立第二套网关 Key/扣费引擎（FR-K02/FR-D01、3.1/3.2）。
- NAS Web 做管理；Mac/Android 做只读连接、监控、缓存和通知；客户端不持有网关管理 Key（FR-K01/FR-K04/FR-C03/FR-C06）。
- 首期不是只读版：包含监控、Key/模型管理、定时能力/质量探针、告警、Mac 连接/自动更新、本项目后续版本兼容、低余额提醒和脱敏诊断（REQUIREMENT 第 11 节）。
- LiteLLM/workbuddy2api 与独立供应商余额为当前数据/管理主线；Ollama 仅做 FR-W02 无推理状态/目录/驻留读取，统计/模型管理/主动探针暂缓，既有 Open WebUI 直连路径不擅改（FR-D01/FR-P04）。
- 质量异常仅告警；探针须显式启用，受已确认周期/预算/并发保护；不安全或未定价对象不能盲测（FR-P03/FR-P04/FR-A01）。
- 本项目从空数据初始化，NAS/Web/Mac/Android 同仓，不默认已有旧 Relay；本项目未来升级保证数据库/API/快照及各端缓存/设置兼容（FR-C04/C05/C06）。NAS 账本为权威，设备只保存必要缓存和本地偏好，禁止客户端另建双写事实源。

### 2.2 推荐选型与待冻结内容

- 推荐：Python/FastAPI 模块化单体、React/TypeScript 静态 Web、PostgreSQL、同仓新建 SwiftUI/AppKit Mac 与原生 Android 客户端；Android 具体技术栈作为 T-01 设计责任，经 Android 17 / Xiaomi 15 验证后冻结。通过 HTTP 适配既有 LiteLLM，采集和探针任务由数据库保存状态，详见 10.6。
- LiteLLM 与 Relay 使用独立数据库/账号，同一 PostgreSQL 实例可承载两库；应用不跨库直接读写私有表。版本兼容与资源占用需 M0 核实。
- 运行时大版本基线、依赖用途和选型理由已给建议，具体补丁版本、镜像摘要、许可证和锁文件待验证后冻结；本轮没有安装软件或新增业务依赖。
- Sparkle 为更新候选；评测优先客观断言，是否使用其他评测工具由实际需求决定。秘密保护与备份恢复方案仍按 T-02/T-07 展开。
- T-01～T-07 仍不是已验证详细实现；D-01/02/05～13 已确认，D-03/04 待详解后确认。具体版本锁定、安全实现与环境验证不因产品确认自动完成。

### 2.3 架构结论与阅读入口（本轮规划）

**推荐：一个模块化单体 NAS 应用 + 一个 PostgreSQL 实例 + 原生 Mac/Android 客户端；已有服务采用只读健康/目录适配器。** 业务分模块，部署不拆微服务；Relay Web 和 API 同源、同镜像；客户端与 NAS 通过版本化 HTTP 合同解耦。已有各服务 Web UI 作为独立入口，不由 Relay 重做或嵌入。

| 选择 | 本项目规划 | 主要依据/约束 |
|---|---|---|
| 运行单元 | 通常新增 `relay`、`postgres` 两个常驻容器；Mac 为独立 arm64 应用，Android 客户端为独立原生应用 | NAS 已有网关，不重复部署 LiteLLM；数据库初始化/升级为一次性操作，不另建常驻迁移服务 |
| 服务端 | FastAPI + asyncio，首期单进程运行采集/调度和 API | 当前是外部 HTTP 集成与受限并发探针；任务/预算持久化，不靠内存保证可靠性 |
| Web | React/TypeScript 静态管理端，随 Relay 镜像发布 | 不需要常驻 Node、独立前端容器或新增 Nginx；不确定视觉稿 |
| 数据所有权 | LiteLLM 管调用 Key/路由/原始调用记录；Relay 管采集副本/监控策略/探针预算/告警/设备 | 同一数据库实例不等于共享表，Relay 不是第二套扣费网关 |
| Mac | SwiftUI/AppKit + URLSession，只连接 NAS；本地只有缓存、设备凭据和偏好 | macOS 27、M 系列、非 App Store；不复制供应商管理能力 |
| Android | 独立原生只读客户端，与 Mac 共用版本化 API/设备配对合同 | Android 17 / Xiaomi 15 纳入范围已确认；设备实际 OS/HyperOS、分发/签名和通知能力需核实 |
| 网络 | 项目交付可配置端口；用户自行配置外部 HTTPS 反代 | 不管理 Lucky，不挂 Docker socket，不默认发布数据库端口 |
| 外部服务监控 | 通过逐服务公开健康/目录接口和受限配置接入 | 不通过 Relay 控制容器；无 Docker socket；内嵌服务 UI 不作为健康判定 |
| 演进 | 有实测瓶颈后从同镜像拆 worker，再评估队列或多副本 | 不提前引入 Redis/Celery/Kubernetes/向量库/分析集群；不因容器更新发现而授予 Docker 写管理权 |

版本/组件及选型理由见 10.6；版本升级见 10.7；本轮工程蓝图见 10.9；实施工作包沿用第 12 节。D-03/D-04 只阻塞对应适配/正文分支，不阻塞身份、数据库、合同和客户端框架的设计。服务管理工作区按 WP-3 切片交付，见 5.2；完整工作包见第 12 节。

### 3.2 兼容性验证输出

针对每个外部端点记录：安装版本/摘要、来源、实际路径/方法、所需权限、响应字段、是否触发真实推理/写入、计费可能性、许可限制、测试时间及通过/失败/未执行。

只读首次接入应验证不触发模型推理。健康端点、数据库日志和 YAML/API 可写能力不能仅靠名称推断。无权限、未支持、未配置、未验证单独呈现；实际余额认证由 E-03 核实。

### 3.3 拟实施操作合同（PROPOSED；未存在的接口）

使用 10.6 的同源 Web + 版本化 REST API，不额外新增 GraphQL/实时消息服务。通用管理命令包含操作 ID、目标稳定 ID、预期资源版本与脱敏参数；客户端操作 ID 不是授权证明。服务端鉴权、校验目标/版本/范围后才执行。相同幂等键与相同参数返回同一操作的状态，参数不同拒绝；一次性交付秘密只限首次响应，不在重试/操作查询中回显；高风险确认绑定目标、参数摘要与版本，防止确认后扩大影响。

| 操作与来源 | 调用身份及必要输入 | 结果/失败语义 |
|---|---|---|
| 监控快照/详情（FR-C02/FR-D06） | Web 会话或只读设备；实例过滤、分页/游标、已见版本 | 返回 schema/API 版本、快照版本、源/采集时间、覆盖/缺失、稳定 ID；ETag/未修改响应不能掩盖时效变化。首页/详情同一事实口径 |
| 接入暂停/移除（FR-M03） | Web 管理员；目标、动作、依赖预览与版本 | 本地状态提交后停止新采集/任务；在途单列。远端删除不是此动作，按独立命令确认；关联历史前验证身份 |
| Key 创建/轮换（FR-K05） | Web 管理员；实例、允许模型、预算/到期、轮换次序 | 网关写入不在本地事务内假装原子；记录操作并读回结果。一次性秘密不持久化为可回读操作响应，重复查询仅给脱敏结果；丢失后核对/撤销/重建 |
| 探针暂停/恢复/手动运行（FR-P05/P06） | Web 管理员；全局/实例/计划范围、预期策略版本 | 自动与手动共用有效暂停/预算检查；返回有效状态、阻塞层级、在途任务及覆盖。恢复不隐式补跑；无价/不安全/不支持不调度 |
| 通知静默（FR-A02） | Web 管理员；范围、到期时间、原因 | 仅控制通知资格；检测/事件持续。拒绝含糊范围或无有效期限；返回当前静默/剩余时间，解除后用摘要而非历史逐条重发 |
| 版本协商/升级状态（FR-C05） | 普通只读设备；客户端应用/API/缓存版本、服务身份 | 兼容返回版本化快照；不兼容显示最低要求/升级入口，维护中暂停刷新保留缓存；设备不获 NAS schema 写权 |
| 正文事件接收（FR-D05） | 独立来源凭据；事件/请求 ID、策略版本、内容类别、原始时间 | 验证来源和范围、去重、落库后才确认接收；旧策略/超期内容拒收，不让重试改写 TTL；日志不打印失败载荷 |

一致性错误区分无权限、版本冲突、功能不支持、策略暂停、预算不足、上游失败与结果未知；不都转成“请求失败”。管理操作以 `pending/applied/rejected/indeterminate` 查询真实状态。外部网关无可用幂等/读回能力时，不承诺 exactly-once；未知结果禁止盲目重试。普通网络重试不得触发第二次付费调用。

灾备恢复是受控运维流程，不默认开放公网“上传数据库并恢复”API；流程见 11.3。具体会话/配对 TTL、幂等记录保留期、分页和载荷上限由 T-02/03 设计并验证，不能写为当前已生效值。

## 4. 数据、兼容与生命周期准备

### 4.1 待定义的数据边界（非已选 schema）

### 4.2 生命周期约束

已确认：元数据默认 180 天，日/月聚合 2 年；正文默认关闭、开启后 7 天；探针证据默认 90 天；告警默认不自动过期。各项可配置，缩短/清理须预览并确认（FR-D04）。

D-04 仍需限定正文范围；D-10 已接受默认边界/目标，但需 T-07 落实备份执行/容量实测和恢复路径。禁止声称删除在线数据已经同步删除所有备份。恢复时已过期正文不能重新暴露。

### 4.3 本项目升级与回滚责任

- 首装使用空数据库和空缓存，不探查/清理用户旧 Relay/iCloud 数据。参考源码仅复用协议/原生 UI，不继承旧产品账本格式。

- NAS 发布包含 schema/API/快照版本与最低兼容客户端要求；Mac 迁移分可重建缓存和不可重建设置。操作前备份，迁移后核对稳定 ID、金额/统计、任务/告警、访问权限。
- 失败/未完成迁移保持维护或只读状态；禁止第二个执行主体同时调度。数据库向后不兼容时不能仅降级镜像，需按恢复流程还原匹配数据库/秘密依赖。
- 当前没有已执行的升级脚本、备份或迁移结果；具体支持窗口与合同测试需实现前冻结，见 10.7。

#### 服务、模型分组和代理额度视图

- 服务分组：支持按服务类型/自定义标签分组（如 AI 网关、Agent、模型运行时、AI 工作台、网络代理），管理员可改显示名称和顺序。分组不改变服务发现、调用路由或安全边界。
- 模型分组：支持“服务/实例 → 渠道/部署 → 模型”层级浏览，也支持管理员创建自定义展示组；同名别名只有在显式映射到同一稳定模型身份后才可聚合。没有映射时分开列示，模型组聚合显示成员、渠道数、数据覆盖和最近观测，避免组级绿灯遮蔽单渠道故障。
- 模型状态字段分列：目录存在、健康端点、自然流量成功/失败和样本时间、Ollama 驻留、主动探针/质量评测证据。无流量为“未知/无样本”，不是成功；正常 GET 检查只能建立其对应的有限证据。
- LiteLLM Key/团队预算（版本与权限核实后）：显示预算上限、已用、剩余和重置/到期信息；调用消费数据可来自已启用 spend logs，但不得因可读 Key 目录就假定能读消费或剩余预算。某些预算语义可能是周期/最大额度，UI 必须依 API 定义呈现。
- workbuddy2api 代理额度：只有在用户运行版本公开只读接口且已验证鉴权/单位/刷新含义后才显示；D-03 未确认前作为标注“可选/待适配”。账号池的剩余次数、并发、冷却状态不能称为货币余额。
- 供应商余额：接入已确认连接器实际提供的数据，保留供应商账户、原始币种/积分单位、来源和更新时间；过期/未知时不作低余额判断。网关费用、虚拟 Key 预算、上游账户余额、代理次数/额度分别呈现，不能简单相加或互相推算。
- 服务首页默认看服务级摘要；可切换模型组、模型/部署明细和“额度/余额”页签；每种指标均展示采集覆盖及最后更新时间。屏幕宽度不足时使用响应式表格/卡片，不在本轮规定视觉稿。

#### 运维工作区

统一 Web 信息架构按“总览、服务/连接、模型/额度、任务/告警、日志/诊断、备份/恢复、版本/审计、系统设置”组织。服务状态是入口之一，不把它误当完整运维能力。页面显示数据必须带来源、最后成功时间/新鲜度、覆盖范围和支持能力；无 API、无权限、未配置、错误响应、过期缓存均是不同状态，禁止将缺失能力转换为零值或健康。服务 API 未提供容量、备份、镜像 digest 等数据时，只显示“未接入/未知”与人工操作指引，不推断 NAS 主机事实。

| 工作区 | 首期页面职责 | 安全/实现边界 |
|---|---|---|
| 总览 | 服务、模型分组、额度/余额、活跃告警、最近任务、采集新鲜度、Relay/数据库容量摘要（容量仅限本应用可测范围） | 只聚合已取得数据；不以未知/过期填零或绿色；宿主 NAS/其他容器容量未接入时明确标注 |
| 服务/连接 | Relay 内连接项 CRUD、连通测试、分组、UI 深链、只读检查能力/频率、凭据轮换 | 保存凭据引用，不回显；测试只打无推理接口；目标服务配置不被顺带修改 |
| 模型/额度 | 分组/渠道/部署/模型目录、自然流量、运行状态、探针证据；Key 预算/消费、代理额度、供应商余额分栏 | 不把目录和实际推理混同；单位/对象/周期不兼容时禁止合计；workbuddy2api 按 D-03 待定能力降级 |
| 任务/告警 | 定时采集、健康检查、余额刷新、探针、告警的历史/下一次运行/耗时/覆盖/原因；允许刷新只读检查、暂停 Relay 任务 | 重试必须幂等；付费探针先经过 FR-P05/P06 预算许可，不能把失败任务重试成额外费用 |
| 日志/诊断 | Relay 结构化运行日志、服务健康历史、错误分类、trace ID、脱敏诊断复制/导出；按权限读取来源 API 提供的日志 | 正文严格遵循 D-04；不记录/回显秘密；外部日志是否可取按 API 权限标注 |
| 备份/恢复 | schema/数据版本、备份操作说明和检查清单、恢复前风险；状态/进度仅在有受支持的登记/数据源时显示 | 首期页面不直接执行 DB/卷恢复、不清理永久告警或宿主机文件；受控恢复按 FR-O03 单活/暂停/撤权规则 |
| 版本/审计/设置 | Relay 版本与 API/schema 兼容、可得的外部应用版本和容器镜像更新状态；Relay 操作审计、管理员/设备、保留期/检查频率 | 更新判断只依据服务 Web/API 或明确授权的只读元数据 API；容器运行 digest 未知时如实显示未知。Docker pull/recreate/restart、数据库迁移默认走手册和 UGOS 运维，不授予 Relay Docker socket |

权限分三类并在 UI 上区分：**Relay 本地设置管理**可由 NAS Web 管理员在审计下执行；**目标服务 API 写管理**中，LiteLLM Key/模型/路由已纳入首期，按 FR-K02/FR-M02 验证和确认；Hermes/MetaCubeXD 等新增写管理需另行确认范围，不由服务管理页面自动开放；**基础设施操作**（Compose/容器/数据库/宿主卷）首期以观测和指引为主，不在 Relay 内执行。任何未来扩展执行权都需独立 O 授权、最小权限代理、安全审查和回滚验收。

所有健康结果必须采用多维状态而非单一绿灯：`process`（进程可达）、`ready`（服务依赖就绪）、`catalog`（模型/配置目录可读）、`model_runtime`（模型加载/驻留）、`inference`（真实生成验证）。缺少接口、权限不足、接口关闭、超时、旧缓存、未测试分别表达，不能降格成“健康”。共享探测频率设有上限、随机抖动及失败退避，避免所有客户端/服务同步轮询。

#### 模型状态与零/低 Token 检查

首选“零推理”分层：①读取服务健康 API；②读取模型/部署目录；③读取 Ollama `/api/ps`（只反映已加载状态）；④读取已有业务调用的成功/失败统计（不额外造调用），并显示数据延迟/采集覆盖。前三层不发送提示词、不加载模型、不计模型 Token。对 LiteLLM/OpenAI 兼容 API 而言，目录端点成功通常只证明配置/可见性，无法证明上游凭据、路由或推理链路可用；应明确这一能力差异。

若管理员另行要求验证端到端推理，提供单独的“真实调用检查”能力：明确模型、端点/部署、可能费用/供应商计费、请求数上限、最大输出 Token、超时、是否自动重试（默认否）、是否允许 fallback（默认否）及结果留存；需预算预留与高风险确认。可限制输出 `max_tokens`/等价项为很小值，但输入提示本身也计费，且零输出参数不保证 provider 无最低费用；不能宣称“几乎零成本”或以健康 GET 替代推理。Hermes Agent 对话和 Open WebUI 交互绝不作为后台探针。

模型维度状态至少拆成：目录可见、路由配置、近期自然流量观测（样本量/时间窗/来源）、主动推理探针（若授权）、状态新鲜度。无自然流量且未探针时为 `unknown / not tested`，绝不能显示为可用；小样本成功也不是稳定性或“模型能力/质量”证明。性能/质量评测属于既有预算保护探针，和无 Token 健康监控分开展示。

#### 容器镜像更新发现（需求已纳入；安全数据源与实现待验证）

需求要求呈现容器镜像更新状态，但 Relay 作为普通 NAS Docker 容器不应假设能读取 Docker daemon 元数据。接入优先级为：①目标服务 API 明确报告版本/digest；②管理员实际配置并授权、无需共享文件系统的只读 HTTP 元数据 API；③均不可用时将运行版本显示“未知/未接入”，仅给人工 UGOS 核对指引。可单独展示 registry 中某标签当前 digest，但不能以未知运行 digest 推断“有更新/已最新”。不默认新增 broker、挂载 Docker socket 或要求宿主机权限。

基础设施更新仍由 UGOS/Compose 运维流程执行；Relay 不自动 pull、重建、重启或回滚容器，不触碰其他容器数据卷。不可访问 Docker API 时，运行 digest 状态为未知；不通过挂载主机路径、遍历配置文件或推测标签来伪造完整清单。

#### Android 在统一运维中的位置

Android 是同仓独立的只读设备客户端，与 Mac 使用同一服务事实源和设备权限；详情与告警可跳转 NAS Web，由浏览器重新进行管理员鉴权。Android 技术/合同/存储/通知/分发建议集中在 10.10，工作包为 WP-6A；统一 Web 的存在不使手机获得上游或基础设施写权限。

#### 页面实施分期建议（不删减已确认需求）

为避免首版把所有外部 API、日志、余额和基础设施能力绑成一个无法启动的整体，建议按可交付价值和权限风险切片；分期只安排先后，不代表把后续能力从已确认范围移除：

1. **运维骨架与零推理状态**：登录/权限/审计基础、Relay 自身健康、服务连接项与 WebUI 深链、LiteLLM/Hermes/workbuddy2api/Open WebUI/Ollama/MetaCubeXD 的支持矩阵、单项无推理检查、最后检查时间/失败原因/未知态。先冻结每个接口的版本与认证方式；不可用服务仍可配置 URL 和标记“未接入”。
2. **统一模型与额度视图**：LiteLLM 模型/部署及自然流量状态、明确身份映射和自定义分组；接入经支持矩阵验证的 Key 预算、供应商余额、workbuddy2api 额度。每个数据源独立标覆盖/新鲜度，不能以页面完成作为字段已可读的证明。
3. **任务、告警和诊断**：展示持久任务历史/下一次执行、重试与暂停规则、已有告警/低余额提醒；Relay 日志与脱敏诊断先行，外部日志仅逐服务在明确 API/权限/正文策略下增加。付费探针继续使用既有预算和明确授权，不混入服务心跳。
4. **恢复、版本与容量运维**：交付人工备份/恢复指引、schema/兼容状态、操作审计及可获得的存储摘要；先验证数据源，拿不到 Docker/NAS 主机指标时明示未接入。容器更新状态有需求，但显示更新状态不等于 Relay 执行升级；实际发现依赖安全只读数据源。
5. **后续扩展闸门**：目标服务（LiteLLM 既有确认管理功能除外）的配置写管理、自动执行容器更新、Android 推送服务均需分别评估和授权。不能为了“统一管理”而默认加入 Docker 写 socket、自动扫描、写凭据或外部推送依赖；Android 基础客户端自身属于已确认范围。

首期使用多维状态合同，避免一个枚举同时混用“接口支持”“健康”“过期”：

| 维度 | 建议字段与值 | 判定边界 |
|---|---|---|
| 接入/能力 | `configured/enabled`；每项能力 `supported/unsupported/unverified/unauthorized` | 关闭监控、没有能力、尚未验证和无权限分别说明；不能通过目录接口猜测其他能力 |
| 检查结果 | `process/ready/catalog/model_runtime/inference` 各自 `success/failure/unknown/not_tested` | 只更新实际取得证据的项；目录成功不使 inference 变成功；驻留为空可为正常观测结果 |
| 数据时效 | `last_checked_at`、`last_success_at`、`source_at`、`fresh/stale/never_observed` | 本次请求失败与保留的旧值并存；未检查与超期分开，附超时/HTTP/权限分类 |
| 更新比较 | `update_available/up_to_date/update_status_unavailable`，含原因与比较时间 | 必须有同一镜像来源/标签、可信运行 digest、正确平台 manifest；仅应用版本或 registry tag 不足以判定镜像更新 |

状态同时带适配器版本和证据来源。只要求准确表达实际支持情况，不要求所有服务具备 ready/catalog。运行 digest 或身份/平台不明、鉴权失败、限流、比较证据过期时均为更新状态不可判定，不能把“查询到 registry”标成“已最新”。

### 9.2 预算、调度和告警时效的量化约束

以下根据现有需求做算术推导，不是模型报价或 NAS 压测。实际目标数按去重后的、安全可测的部署计算，80 仅使用历史别名数量作示例。

- **调用量**：80 个目标 × 每日 48 轮 = 3,840 次可用性起始调用/日。若 1 USD 全用于这些调用，平均单次必须不超过约 **0.0002604 USD**；能力/质量、重试、裁判和其他费用还会进一步压缩该额度。
- **质量采样**：采用尚未确认的“10 个用例 × 每例 3 次”时，Top 5 每个模型一个部署就需要 150 次调用/轮；每模型两个部署则为 300 次。首次基线另需采样，不能把基线费用排除在日预算之外。
- **串行容量**：并发 1、80 个目标在 30 分钟内完成，单个目标平均总占用须低于 **22.5 秒**，且这还没给其他主动测试留时间。慢响应/超时会使轮次逾期；禁止旧轮未结束又无限堆积新轮。
- **可用性告警**：按每 30 分钟一次、连续 3 次失败的提案，持续故障约需 **60～90 分钟**确认；连续 2 次成功恢复约需 **30～60 分钟**。前提是每轮均实际执行，预算暂停或排队会延长时间。
- **质量告警**：按每 24 小时一轮、连续两轮下降的提案，已有基线时约需 **24～48 小时**确认；新基线、样本不足和预算暂停会更久。这些提案不提供实时“降智检测”。
- **容量规划**：元数据估算量 = 日请求数 × 180 天 × 实测单条含索引占用；正文另计日采集量 × 7 天；证据按日探针量 × 90 天；永久告警和备份单独增长。日请求量、单条大小和可用磁盘未知，D-10 的恢复时间目前无法承诺。

实施建议：启用页同时预览费用和执行时长；展示最后检测、下次计划、实际延迟和覆盖。D-07 的“公平轮转”需实测具体份额和最小有效轮次，否则能力/质量可能永远得不到预算，见 11.1。

## 10. 建议实施架构与核心规则（PROPOSED）

本节提供可评审的推荐方案；产品选择沿用 REQUIREMENT 第 13 节，只有 D-03/D-04 仍未决。T 项技术细则为 PROPOSED，不将技术建议写成新增产品确认。

### 10.1 部署与数据流

推荐首期使用 **一个 Relay 应用服务承载 API、编译后的 Web 静态文件、采集与调度**，配合持久化存储。Web 与 API 同源，Mac/Android 连接用户配置的服务地址；用户可以自行在 Lucky 设置 HTTPS 反代，本项目不接管反代配置。请求采集、供应商读取、管理和主动探针分别限流，付费探针并发 1 不应阻塞登录或界面查询。

在 D-02 选择完整原生 Key 管理的前提下，推荐一个受支持的 PostgreSQL 实例，分别建立 LiteLLM 与 Relay 的独立数据库/账号；已有可用实例则优先复用。Relay 经验证的接口采集网关数据，不依赖直接读写 LiteLLM 私有表。两库分别迁移、备份并记录恢复顺序，共享实例的故障影响需要纳入恢复验证。相比再为 Relay 增设一种存储，该方案减少运维种类；版本基线建议见 10.6，实际兼容与 NAS 部署方案尚待验证。

```text
Web / Mac / Android ──HTTPS反代或局域网入口──> Relay API ──> Relay 独立数据库
                             │
                             ├─ 采集/管理 ──> LiteLLM ──> LiteLLM 独立数据库
                             ├─ 余额适配 ──> 供应商管理接口
                             ├─ 受预算约束的探针 ──> LiteLLM ──> 指定部署
                             └─ 无推理状态/目录 ──> 已接入服务 API

现有推理客户端 ──> LiteLLM ──> 既有上游
可选正文采集：LiteLLM 回调扩展 ──受限异步投递──> Relay 日志入口
```

首期单 Relay 活跃调度实例；任务持久化并使用租约/唯一任务键，避免重启和重复触发。暂不需要 Redis、独立消息集群或专门向量库。推荐的服务语言/Web 框架和运行方式见 10.6；若采用正文扩展，其在 LiteLLM 内运行的薄适配代码独立按网关环境构建和验证，不能强制 LiteLLM 使用 Relay 的 Python 或依赖版本。

### 10.2 模型、Key 与状态的权威来源

- 每个网关是其自身调用 Key、调用预算与路由的权威。Relay 多实例管理使用 `(instance_id, remote_id)` 隔离，同一供应商账户可关联多个实例；账户余额只计一次。
- `model_identity` 是经确认的型号映射，`deployment_id` 是实例内稳定部署，`public_alias` 是调用名称，三者分开。配置摘要、价格和测试版本分别保留；别名变更不抹掉历史。
- Relay 管理写入记录操作 ID、目标及预期版本，状态为 `pending → applied / rejected / indeterminate`。网络超时进入待核对，不因重试重复创建 Key；没有安全的远端核对办法时由管理员处理。
- 外部管理员仍可能直接修改 LiteLLM；目录同步应发现漂移并刷新视图，不能自动把远端覆盖回 Relay 旧配置。冲突写入显示新旧差异。
- YAML 到数据库模型迁移先在验证环境演练导入、名称/部署核对及回滚；正式切换需明确移除旧声明的时点和维护窗口，避免双路由。基础设施仍由指引执行，Relay Web 不获得 NAS 文件写权限。

### 10.3 采集、正文与统计

- 元数据采用分页读取 + 有界时间窗口 + 重叠回查，按源稳定请求/尝试标识幂等合并。游标与数据同事务提交；聚合基于唯一记录更新，修正记录先扣旧贡献再计新值，避免重放累计。
- 页数/总数可能截断或是近似值，不能仅按 `total_pages` 停止采集。对当前版本验证遍历终止方式、排序稳定性和迟到记录回查上限；超过已覆盖窗口的数据缺口明确显示。
- “用户逻辑请求”只能在可信归属、网关请求与内部重试关联可得时计数；不同客户端独立重发默认是不同网关请求，不能仅凭内容相同推断为同一用户意图。Hermes 嵌套调用需关联或分别展示，不重复算作一次端到端费用。
- 正文推荐由来源端明确筛选后异步投递，Relay 入口独立鉴权、限体积、按事件 ID 去重；不照搬将秘密打印到日志的示例。以 `source_request_id` 关联元数据，可先有一方后补齐另一方。
- **交付保证建议**：Relay 不可达时普通推理继续；正文允许出现可见缺口。事件仅在持久化后确认收到，有限重试需有过期时间；若要求断网期间正文也不丢，需设计源端持久缓冲、加密/空间/清理和相应部署变更，再确认 D-04/D-10。官方回调本身不证明可靠重放。
- 保存政策带版本和生效时间，关闭后不得接收队列里过时的新增正文。来源端过滤、Relay 存储、错误日志和备份分别验证；过期正文先在读取时拒绝，再异步清理，不能等清理任务运行才失效。
- 金额使用明确币种/单位的十进制定点表示；网关计费、供应商账单和余额为独立数值。人工价格/汇率更改需新版本，历史重算作为单独标明的估值，不静默改写既有账单或已完成预算日。

### 10.4 调度、质量与告警

-  1 USD/日及并发 1 以 **一个 Relay 服务所连接的全部实例合计**为作用域，D-07 已确认该作用域，配额细则由 T-04 验证；新增实例不自动乘出新预算。单独部署的其他 Relay/网关内置健康任务不在此保证内。
- 计划唯一键包含计划、轮次、部署、测试版本；任务冻结范围/参数后进入 `queued → reserved → running → succeeded / failed / uncertain`，未开始任务可为 `paused/skipped`。队列逾期不自动补跑多轮。
- 费用预留和任务领取原子完成；崩溃或调用超时后结果未知的任务不自动再付费执行，先核对且保留可能已产生费用的预留。预算归属按开始日，并明确跨日未结算任务；时间/时区变化不能清零在途支出。
- 先预留达到最低有效样本所需的当轮额度，再启动能力/质量轮次；不足时明确延期。失败样本不作为正常质量不合格直接计分；无法完成的轮次不产生“完整通过”。
- 基线键包含部署、已知上游版本/配置指纹、测试集、评分与参数版本。首次运行建立候选基线，建议管理员确认后启用比较；变化后新建版本。模型真实版本不可见时显示该限制，不声称已锁定供应商内部模型。
- 告警按实例/部署/类型/规则版本关联事件，异常产生、持续更新、恢复分开；已读状态不覆盖事实事件。预算暂停和过期不是恢复成功。无新样本时不累计成功/失败计数。
- 按 FR-P06/D-07，依赖证据到期或关键指纹变化时基线失效，停止当前质量回退判断，在预算内安排重建；原样本按保留策略删除。可保留不含正文的版本/评分摘要及历史告警，但必须标记证据过期且不能据此继续作当前比较。

### 10.5 Mac、新项目初始化和自动更新

- 同仓 `mac/` 新建仅面向 M 系列/Apple Silicon、macOS 27 的原生 SwiftUI/AppKit 客户端，采用站外分发、不上 App Store；参考旧工程的菜单栏/详情及解析规则需核对许可与 UI 保护，但不修改旧仓库、不继承旧账本/iCloud 同步。
- 配对码单次短时兑换独立可撤销设备凭据；普通设备只读。本项目不建立“Mac 导入旧数据”的特权 API，设备的本地设置迁移不会赋予 NAS 管理权限。
- NAS 保存唯一远程事实源；Mac 只持有服务身份/设备凭据、偏好和缓存。新版本协商成功后按快照版本更新首页/详情，事件独立游标；时效按源事件→入库→显示验证。
- 自动检查/下载、用户选窗口安装/重启已确认；更新包签名和应用签名/公证分别验证，发布私钥不随 NAS/Mac 分发。Sparkle 2 是候选，不代表已安装或兼容目标 SDK。
- 版本升级前保护不可重建设置，API/schema 不兼容时阻止不安全写入和盲目读取，显示服务/客户端升级建议；支持窗口建议见 10.7。

### 10.6 明确架构推荐：模块化单体 + 既有网关 + 原生 Mac/Android 客户端（PROPOSED）

**推荐组合：Python/FastAPI + React/TypeScript/Vite + PostgreSQL + SwiftUI/AppKit，Android 原生候选 Kotlin/Jetpack Compose；UGOS PRO Docker Compose 部署，项目交付 Web/API 端口，外部 HTTPS 反代由用户自行配置。** 选择依据是当前工作以供应商 API 集成、日志采集、统计和低并发评测为主，已有 LiteLLM 承担推理路由、原生 Key 与调用预算；业务量与团队规模均没有证据要求分布式系统。以下是面向本项目的设计判断，不是框架性能排名。

| 管理 Web | React 19 系列 + TypeScript + Vite | 表格/筛选/详情/状态交互；编译成静态文件随 Relay 镜像发布，Node 只用于构建。路由和服务端数据缓存采用 React Router/TanStack Query，版本按 React 兼容组合锁定 |

| Android | Kotlin/Jetpack Compose 为原生候选；HTTP/本地存储库及版本待选 | 同仓独立 `android/`，共用 NAS 版本化合同、设备/告警语义；工具链、target/min SDK、签名分发和后台机制需经 E-07 验证，详见 10.10 |
| 计划和执行 | asyncio + PostgreSQL 任务/租约/预算记录 | 原生周期足够当前分钟/天级计划；任务可靠性由数据库状态承担。无需首期增加 Redis/Celery，不把内存定时器或 FastAPI BackgroundTasks 当持久队列 |
| 部署 | UGOS PRO Docker Compose + 既有 LiteLLM；反代用户自配 | 构建静态 Web 和 Python 运行镜像；通常新增 `relay` 与 `postgres` 两个常驻容器，若已有可用 PostgreSQL 则只新增 Relay。NAS 首验 Linux amd64，其他架构另验证 |

PostgreSQL 的镜像标签按用户选择使用 latest，不再要求固定到 17/补丁号；数据库主版本升级独立安排，实际 digest 留作验证/恢复证据而非默认绑定到 Compose。其他运行时/依赖的大版本仍是建议兼容基线，未声明已安装、已实测或为最新版本。实施前产出精确锁文件、镜像摘要、许可证和目标架构安装结果；TypeScript/Vite、路由/缓存库等具体版本届时一起固定，避免凭文档填写未经组合验证的补丁号。当前没有批准部署、付费调用或数据迁移。

依据：[FastAPI 异步说明](https://fastapi.tiangolo.com/async/)、[Python 版本状态](https://devguide.python.org/versions/)、[PostgreSQL 支持周期](https://www.postgresql.org/support/versioning/)、[SQLAlchemy 异步会话](https://docs.sqlalchemy.org/en/20/orm/extensions/asyncio.html)、[psycopg 异步支持](https://www.psycopg.org/psycopg3/docs/advanced/async.html)、[Alembic](https://alembic.sqlalchemy.org/en/latest/)、[HTTPX](https://www.python-httpx.org/async/)、[Pydantic](https://docs.pydantic.dev/latest/)、[React 的 Vite/路由/数据获取选项](https://react.dev/learn/build-a-react-app-from-scratch)。Web 是登录后的管理工具，当前没有 SEO/服务端渲染要求，因此选择静态 SPA；页面路由、数据缓存及错误状态仍需要实现。

#### 内部按业务模块组织，统一发布

这些是一个应用内的代码职责，不是六套独立服务；不强制每个模块建立重复的 Controller/Service/DAO 层。

#### 运行、通信和恢复规则

1. **一个应用镜像、首期一个 Uvicorn 进程**：FastAPI lifespan 管理连接池和异步采集/调度循环；Web 请求、采集、探针分别设置连接/并发上限。调度任务异常有明确失败状态和监督恢复，不让循环静默退出。多进程启动会复制生命周期任务，后续扩容前必须拆执行角色或验证单领导者机制。[生命周期依据](https://fastapi.tiangolo.com/advanced/events/)
2. **先持久化再执行**：管理员触发任务先写数据库并返回任务 ID；调度器读取到期任务，短事务领取并预留预算，然后释放数据库锁再请求上游。结束时另一个事务提交结果/费用/告警；探针网络等待期间不占有长事务。租约用于协调执行，不宣称能让外部付费 API 恰好执行一次。
3. **简单 HTTP 合同**：以版本化 REST/JSON API 开始，Web 同源访问，Mac 使用 URLSession，Android 使用经 T-01 验证的原生 HTTP 客户端。快照带服务身份、数据版本和采集时间；使用条件读取/分页和告警游标，刷新周期采用 D-05 最终值。首期轮询即可满足当前秒/分钟级展示目标；无必要先建 WebSocket。若以后确认更低延迟通知，再增加 SSE，断线仍以数据库事件游标补齐。
4. **有限本地计算**：网络 I/O 异步，重 CPU 的可信评测/大导出需要移出事件循环并限制资源；模型生成代码在 API/调度进程中不执行。若具体测试必须执行生成代码，需单独设计无秘密、受限网络/文件/CPU 的隔离执行环境，不把普通 Python 子进程当安全沙箱。
5. **单库内明确生命周期**：Relay 关系数据、受控文本正文、合成证据先保存于 PostgreSQL 的分离表，分别过滤权限和执行保留策略；大附件不默认入库。预算/任务/游标作为恢复所需状态保存；金额为定点值，不能用浮点累计。LiteLLM 表由 LiteLLM 管理，Relay Alembic 只改 `relay` 库。
6. **故障可解释**：Relay 停止时现有客户端仍可经 LiteLLM 推理；Relay 数据库不可用时管理写入/新付费任务暂停，Mac 显示离线缓存。共用 PostgreSQL 实例故障也可能影响 LiteLLM 鉴权/调用，这属于共享故障域，部署恢复验证需要覆盖，不能承诺绝对互不影响。
7. **部署边界**：使用原 Compose 的现有网络，跨 Compose 引用时才声明为外部网络；数据库不发布宿主端口，Relay 提供明确 Web/API 监听端口。Lucky 域名/证书/规则由用户配置，不需要向项目提供。Web 静态资源直接随后端提供，不新增常驻 Node 或 Nginx。数据库拟默认用 Docker 命名卷；已有 Compose 若使用目录挂载则尊重现有选择，不为设计索要宿主机路径。程序目录随镜像交付，不要求另建 Relay 业务工作目录；数据库不放进 iCloud/同步目录。备份目标由部署者选择，策略与密钥恢复按 D-10/T-02 实施，持久卷不能代替备份；说明见 DEPLOYMENT 1.1/2。

该规模下，自建的部分是探针预算、任务状态和业务规则；HTTP、验证、数据库事务和迁移使用成熟组件。FastAPI 的请求后置任务并不代替本方案的持久调度；官方也将重型跨进程任务与轻量后置任务区分，见 [BackgroundTasks](https://fastapi.tiangolo.com/tutorial/background-tasks/)。

#### 取舍与演进触发条件

- 选择 Python 是为了减少当前集成/评测与日志扩展的语言切换；Go/TypeScript 同样可实现服务端，但本项目尚无可复用的该类后端代码，也没有需要通过换语言解决的实测瓶颈。若后续证明运行内存或 CPU 不达标，先定位工作负载再调整，当前不作语言性能承诺。
- 选择 PostgreSQL 是因为完整 LiteLLM Key 管理已引入该前提；Relay 再用 SQLite 会增加第二种存储与备份路径。推荐共用数据库服务、分开数据所有权；数据库主版本升级独立于 Relay 应用发布。
- React 管理 Web 与 Swift 原生 Mac 各自负责最适合的展示；复用 HTTP 合同和测试数据，不为追求同一套 UI 改成 Electron/Tauri，保持已选择的原生 Mac 体验方向，不为共享代码引入第二套跨平台桌面运行时。
- 先保持一个发布单元；当执行任务持续影响 API 延迟、需要多个 API 副本、或评测计算量明显上升时，**优先把同一代码库/镜像的 worker 独立成进程或容器**，保留 PostgreSQL 任务合同，再评估是否需要消息队列。无需先拆微服务。
- 上游接入通过版本化适配器和固定合同隔离；长期历史查询变慢时先检查索引、按时间分区/归档和聚合，只有实际数据量要求时再评估专用分析库/对象存储。

架构可据此进入接口与数据字典设计。D-01/02/05～13 已明确产品方向：单管理员/多只读设备、LiteLLM 可加数据库、刷新/汇率默认、全局探针预算、空数据新项目、同项目升级/恢复控制、统一运维 Web、Android 客户端和容器更新状态；D-03/04 尚待范围选择。配额数值、版本支持窗口、接口/许可、Android 发布资源及 Docker 只读数据源仍需设计/验证。当前无需修改 AI_CONTEXT 中“无已采用技术栈”的事实。

```text
Relay-Service/

  deploy/       # Compose/建库/备份恢复操作指引，不默认代执行
```

同仓不等于同一二进制或同时强制更新：NAS 端是 API+Web 一个发布单元，Mac、Android 各自为独立签名应用；合同版本协调三端，网关与 PostgreSQL 有各自版本/迁移生命周期。

- 建议首期协议 `v1`，增量字段保持向后兼容；服务端发布声明支持的客户端/API 范围，不用应用 SemVer 直接当 API/schema 版本。
- **兼容窗口建议**：当前 API 主版本至少继续支持前一个已正式发布客户端所使用的兼容合同，破坏性变更先增加新合同并保留旧读路径，明确迁移/废弃期限；具体窗口需由 T-01/07 在发布计划冻结，不能无期限承诺任意旧版本。
- **NAS 常规升级**：备份本项目 relay 库及秘密恢复依赖 → 暂停付费任务与管理写入 → 独立迁移角色取得锁 → expand（增加新字段/可兼容表）→ 验证 → 新 API 服务运行并确认就绪 → 恢复计划；移除旧字段放在兼容窗口结束后的后续版本。模型/Key仍属于 LiteLLM，不被 Relay 迁移直接覆盖。
- **Mac 常规升级**：验证签名/服务要求 → 备份不可重建设置 → 版本迁移 → 可重建缓存失效/重同步 → 首页/详情/通知游标核验。正常升级保留服务身份/设备授权；仅灾备恢复/换 NAS 才按 O03 重新配对。
- **失败路径**：schema 失败不宣称服务就绪，保持维护/只读并给脱敏诊断；Mac 设置迁移失败保留原值，不能以清空所有 Application Support 解决；数据库回滚明确恢复快照及会丢失的升级后写入，不把旧镜像直接起跑当数据回滚。
- **Android 常规升级**：核对签名身份/可信分发与 API 要求 → 保护偏好/设备身份 → 迁移设置 → 失效/重建缓存 → 核对告警游标/通知资格。更新渠道与是否自动下载待 T-07 冻结，不沿用 Sparkle；详见 10.10。
- **回归矩阵**：上一版 Mac/Android+新版 NAS、新版客户端+兼容旧 NAS、不支持组合、旧/新缓存、设置迁移失败、schema 并发锁、数据/预算/告警核验；对应 AC-26/39/51/54/58。真实跨度用本项目将来的发布 fixture 验证，不索要旧 Relay 用户数据。

### 10.8 已选入的低余额提醒与脱敏诊断

- `collector` 按账户保存原币/额度、源/采集时间与有效性；`alerts` 保存账户级规则（开启、低阈值、恢复阈值、币种/单位、冷却）并按账户去重。进入低阈值产生一次故障，达到恢复阈值产生恢复，未知/过期只报告采集状态；多实例引用同账户不重复事件。规则未配置显示待配置，不擅定统一金额。
- Web 在账户详情配置规则、预览单位/阈值和近期余额；Mac 复用通知游标、静默、已读及在线授权流程。此事件不改路由/自动充值，不与 80% 探针预算提醒混为一谈。
- 系统区提供预览/复制脱敏诊断摘要：Relay/网关版本、合同版本、支持矩阵、采集/任务/升级状态、错误类别和追踪 ID。统一脱敏规则过滤秘密、正文、完整内网地址和个人标识；不自动发送第三方，完整诊断包/业务报表不隐含加入。
- 对应 FR-A03/FR-O04、AC-55/56；复用现有模块，不新增短信/邮件/Webhook、独立报表服务或新容器。

#### 10.9.2 代码模块与依赖方向

以业务模块拥有规则/写入入口，不机械建立每个模块一套 Controller/Service/DAO。以下为拟建入口，基础设施保持小而明确，不新增通用插件平台或分布式事件总线。

| 拟建入口（均在 `server/relay/` 下） | 职责与写入所有权 | 对外/协作边界 |
|---|---|---|
| `app.py`、`api/` | 启动组合、鉴权入口、请求/响应、版本化路由与静态资源 | 薄入口，调用业务用例；不在路由里直接解析供应商响应或执行计费逻辑 |
| `access/` | 管理员、会话、配对码、设备、授权代际 | 查询/命令先校验身份；设备只能操作自己的配对/已读/通知游标，不获得业务管理权限 |
| `connections/`、`adapters/` | 网关实例、供应商账户、目录/部署引用、支持矩阵、网关管理操作 | 连接模块拥有凭据引用与目标校验；适配器只做外部协议转换，返回规范化数据/错误，不直接落库 |
| `collector/`、`queries/` | 请求/尝试副本、采集游标/覆盖、余额、聚合与快照；D-04 后的正文策略 | 采集事务由 collector 负责；queries 读取同一事实及聚合，不因页面刷新重新请求上游 |
| `probes/` | 计划、轮次/样本、任务、预算预留/对账、测试/基线 | 依赖已保存目录/价格/覆盖；经 adapter 发送受控推理，不用管理 Key 充当常规探针 Key |
| `alerts/` | 规则/异常恢复、去重、静默、每设备已读/通知游标 | 评测与余额模块调用明确告警用例；事件落库后才能向客户端展示/通知，不把通知发送作为事实来源 |
| `compatibility/`、`ops/` | 合同版本、维护/恢复状态、保留清理、脱敏诊断 | Relay 迁移仅管理 relay 库；不控制 Lucky/NAS 容器，不开放公网整库恢复接口 |
| `infra/`、`migrations/` | 数据库会话工厂、受控 HTTP 客户端、秘密加解密、配置、迁移文件 | 提供技术能力，不嵌入余额阈值/选模/告警等业务规则；不设共享全局 AsyncSession |

依赖方向：`api → 业务用例 → adapter/infra`；外部响应经 adapter 规范化后进入业务模块，Web/Mac/Android 仅依赖 HTTP 合同。queries 可跨本项目只读记录构建视图；跨模块写入必须经过拥有者用例，不通过随意互改 ORM 对象形成循环依赖。共享 DTO/错误位于小型合同包，不共享上游秘密对象。

#### 10.9.3 数据归属、合同与读写模型

在 4.4 逻辑字典上落实以下归属，不新增第三份事实账本：

| 数据 | 权威来源 | Relay/设备客户端的保存边界 |
|---|---|---|
| 网关调用 Key、模型/部署配置、网关预算与原始调用 | LiteLLM 的管理/日志 API；文件对象仍按文件来源处理 | Relay 保存稳定 ID/脱敏副本和操作记录；不双写 LiteLLM 私有表，不伪装 YAML 对象已可写 |
| 供应商余额/额度 | 账户对应的实际已验证接口 | Relay 保存有来源/单位/时间的采集快照，不能用估算消费冒充剩余余额 |
| 监控策略、探针计划/费用责任、结果/基线、告警、设备授权 | relay 库 | Relay 负责事务/保留/版本迁移；Mac/Android 仅读取和保存必要缓存 |
| Mac 展示偏好与设备凭据 | 本机设置/Keychain | 本地版本化保护；不上传 Keychain 内容或复制 NAS 账本；缓存可重建，偏好不可随意清空 |
| Android 偏好、设备凭据与缓存 | 手机本地设置/平台安全存储 | 与 NAS 事实账本分离；设置/身份保护、缓存重建、备份与撤销边界见 10.10 |

- 不另建 CQRS 服务或读库：先用同一 PostgreSQL 的规范化记录、日/月聚合及查询视图。请求使用 `(instance_id, source_request_id, source_attempt_id)` 等来源唯一键；标识缺失时采用该源验证过的确定性键/重叠覆盖策略，不凭时间猜测逻辑调用。模式、币种、权限和覆盖与统计值一起返回。
- Relay 内部合同建议 `/api/v1`；浏览器与 Mac 的管理权限并不相同。快照/详情、告警游标、设备配对、管理操作状态及管理员设置为路由组，不混用设备身份执行管理命令。设备已读确认属于自己的受限元数据操作，“只读 Mac”指不能改业务配置/网关/预算。
- 通用响应带 `api_version`、`schema_version`、`service_id`、`data_version`、`generated_at`、来源采集时间及缺失原因；金额使用十进制字符串加币种/单位，时间保存 UTC，预算日和报表按已确认北京时间规则计算。
- 列表用稳定排序与游标分页；快照各字段不是声称同一时刻采齐的全局数据。首页/详情读同一快照版本或显式显示版本变化；新鲜度即使没有新采集也随时间变化，ETag 不能让“过期”状态永久留在客户端旧状态。
- 不支持/未知/未配置与真实零值分开；已删除来源保留墓碑和历史引用。正文独立表/权限/TTL，默认关闭，设备 DTO 和普通诊断 DTO 不包含正文或秘密。D-04 未定前不落地采集回调。
- 首期优先按实例/事件时间、稳定请求键、到期时间、告警序号、任务状态/到期时间建立与查询匹配的索引；大字段不默认保存完整上游响应。分区/对象存储只在容量测算和清理实测证明需要时加入。

#### 10.9.4 调度、事务及核心数据流

**采集路径**：周期到达 → 按实例限流读取已验证 API → 规范化/过滤 → 短事务幂等写入记录并推进游标 → 更新受影响聚合/覆盖 → 生成告警事件 → Web/Mac/Android 读取。网络请求不占长事务，游标不能先于记录提交。只读查询可退避重试；迟到记录采用有界重叠回查，并修正关联聚合，不重复累计费用。

**余额/告警路径**：账户级周期采集 → 保存原币/额度及来源时间 → 判断新鲜度/有效性 → 按账户规则比较低阈值/恢复阈值 → 持久化去重事件 → Web 留存/Mac 在线本机通知。多网关引用同账户不重复告警，未知或过期余额不假装归零；不自动充值或改路由。

**管理路径**：管理员命令/确认摘要 → 保存幂等操作与预期版本 → 调用 LiteLLM → 读回核验 → 保存真实状态/审计。远端与本地不构成跨库原子事务；未知结果转 `indeterminate`，先读回，不自动重发创建 Key/改路由。管理队列不保存一次性交付 Key 的可回读明文，网关返回新 Key 时只在授权首次响应交付。

**探针路径**：选模并冻结策略/测试/部署/价格版本 → 保存任务 → 校验暂停/预算/安全/模式 → 事务领取全局执行许可并预留金额 → 事务结束后发推理 → 保存样本/费用责任与对账 → 评测/事件 → 下一轮。自动与手动共用同一入口，执行前再核对策略版本；暂停后不发新许可，已在途请求独立展示。

- 用数据库行锁、条件更新和唯一约束保证本项目任务领取与预算竞争；首期只有一个持久的全局付费执行槽，目标并发 1。不能只用 Python Semaphore 假装跨重启仍正确。任务租约/心跳用于发现中断，claim token 防旧执行者写入新状态；SQL 锁不保证外部付费 API exactly-once。
- **失联后不盲接管**：已提交/可能提交的请求保留未知费用责任；不能因租约到期就释放预算/执行槽并重发。数据库连接丢失时停止发新推理；恢复后先验证旧执行者停止并核对远端/终态，无法证明时维持暂停并提示管理员。仅证明未发送的任务可安全重新排队。
- 重试分类分开：只读采集可有限重试；Relay 本地命令靠幂等记录去重；外部管理写入和付费推理必须读回/核对或明确失败后重新授权，禁用 HTTP 客户端的无条件推理重试。预算使用定点值，跨日未知请求按原预算日保留费用责任。
- asyncio 周期循环只是“唤醒并查询到期记录”的时钟，计划/任务/预算在数据库；错过周期按 FR-P05/P06 处理，不在启动时堆积补跑。FastAPI lifespan 管理循环与连接池，BackgroundTasks 不作为可靠持久队列。
- 启动顺序：校验配置/秘密 → 连接 relay 库并核验 schema/维护状态 → 恢复游标及识别中断任务 → 放行 API/后台限时只读核对接入能力 → 对可执行对象按已保存启用状态启动计划。外部无响应不阻塞整个 API 启动，中断付费任务未核对前保留对应暂停。首次探针仍默认不开启；灾备恢复保持暂停，不被 restart policy 自动解禁。
- 建议新增 `/health/live`、`/health/ready`（本项目拟定路径，不是 LiteLLM 路径）：live 只证明 Relay 进程可响应；ready 检查自身 schema/DB/维护状态，不触发模型调用。数据库临时失联不把 live 变失败造成无限重启，业务未就绪单独报告；某个外部实例不可用仅降低该实例支持/采集状态，不使整个 Relay 就绪检查失败。关键循环静默退出作为独立故障检测。

#### 10.9.5 鉴权、秘密与网络安全实现方向

- 单管理员首次初始化需要一次性部署侧随机令牌，明文不进入普通日志、不通过未鉴权公网页面泄露；服务端串行完成首次创建后永久关闭初始化入口。密码用 Argon2id 单向校验；重置为受控部署操作，不能靠暴露匿名“重置管理员”接口。
- Web 使用随机不可预测的 opaque session Cookie，服务端仅保存会话 token 摘要/期限/撤销状态；同源请求，启用 HttpOnly/SameSite、写操作 CSRF/Origin 校验。HTTPS 部署启用 Secure Cookie，不把 Cookie 放 localStorage，不因 proxy headers 绕过鉴权。
- Mac 配对码短期/单次/限尝试，兑换高熵设备 token；数据库保存 token 摘要，Mac 存 Keychain，配对返回服务身份/权限。撤销后服务端立即拒绝，客户端保留缓存并明确凭据失效。不用长寿命无状态 JWT 代替可立即撤销的设备身份。
- 需调用外部服务的秘密不能只做 hash：建议用 `cryptography` 的 AES-GCM，独立随机 nonce，附带 secret ID/用途/密钥版本作为关联数据；密文记录与外部挂载的加密主密钥分开。Relay 主密钥、LiteLLM Salt Key、数据库密码、发布签名私钥不混用；常规升级保留，轮换使用版本化重加密/核验流程。丢失 Relay 主密钥时允许重配凭据但不可宣称还能解密原值；备份依赖见 T-02/D-10。
- Relay 管理凭据与探针调用 Key 分开；浏览器/Mac 不持有 LiteLLM Master Key，调用 Key 只授权已选模型/预算。仅“生成了虚拟 Key”不等于最小权限已验证，需核对实际角色与允许路由。
- 局域网 HTTP 与公网 HTTPS 区分：公网访问只走用户自配 HTTPS 入口；可信私网可显式配置 HTTP 访问模式并提示传输不加密，Cookie/客户端 transport 配置按模式处理。不关闭所有证书校验，不让本地 HTTP 例外自动扩展到公网；反代内部 HTTP 是传输拓扑，不是认证替代。
- 网关/供应商 HTTP 客户端只能访问管理员明确登记的目标；私网地址按目标授权，不把“NAS 服务需私网”变成任意 URL 抓取。限制 scheme/port/重定向并复核 DNS/实际连接目标，阻断元数据/未授权地址；可信代理只配置项目收到请求的实际代理范围，不默认信任所有转发头。
- 原始秘密、正文、完整认证响应不进入日志/追踪/审计；诊断默认脱敏、不自动上报。Secret 输入单向、不回显；日志有轮转/大小约束，不为诊断新增常驻监控容器。

安全库的新增理由已纳入 10.6；上述为拟实现方向，不是已通过安全审计。算法与机制依据为 [Argon2id](https://argon2-cffi.readthedocs.io/en/stable/argon2.html)、[认证加密](https://cryptography.io/en/latest/hazmat/primitives/aead/)、[Apple Keychain](https://developer.apple.com/documentation/security/keychain-services)；依赖具体版本/许可/安装待 WP-0/1 验证。

#### 10.9.6 Web 与设备客户端内部组织/同步

- **Web**：按 5.2 八个运维工作区组织路由/功能，访问管理归入系统设置并提供明确入口；React Router 做导航，TanStack Query 管服务端数据/轮询/失效，局部表单用组件状态，不默认增加 Redux。API client 统一认证失效、超时、缺失状态和追踪 ID；新增/变更成功后刷新有关缓存。Key 一次性响应不进入持久缓存/持久状态，正文查看不进入常规浏览器离线缓存。
- **Mac**：`APIClient`（URLSession/合同 DTO）→ `SyncCoordinator` actor（串行同步、版本/撤销/游标）→ 展示用 ViewModel → SwiftUI/AppKit 菜单栏/详情。缓存写入由统一存储边界负责，通知由独立本地协调器读取服务端资格/游标，不在各页面各开采集任务。
- **本地保存**：小型只读快照/游标采用版本化 Codable 文件并原子替换，设置独立保存、设备 token 入 Keychain；首期不为监控缓存新增本地关系账本或 iCloud 双写。大列表按需分页，不把 180 天服务端历史全量同步到 Mac。
- **同步**：在线按 D-05 刷新；重新联网先核验服务身份/合同/设备权限，再同步快照和增量事件，详情随数据版本刷新。读取重试使用有上限的退避/抖动；醒来/换网触发去重同步，不重复补发大量本机通知。服务端历史完整保留，通知摘要/已读遵循 FR-A02/设备规则。
- **状态**：首次加载、空、真实零、未知/部分、过期、离线缓存、凭据撤销、不兼容、维护/迁移失败分开。缓存显示原采集时间，不用当前刷新时间伪装新鲜。Mac 只能修改自己的连接/偏好/通知/已读，配置管理通过打开 NAS Web 完成。
- **更新**：Sparkle 2 系列作为推荐更新实现；固定 Bundle ID、站外签名/公证、HTTPS 更新源、更新包签名和兼容检查。安装窗口由用户选择，更新前保护不可重建设置；NAS 与 Mac 不强制同时升级。实际 SDK、签名资源和更新安装仍是发布前验证，不索要旧 Relay 数据。

### 10.10 Android 客户端详细方案（PROPOSED；FR-C06/D-13 范围已确认）

Android 在同仓 `android/` 独立构建，Kotlin/Jetpack Compose 为候选。它与 Mac 共用服务端合同和业务口径，各端使用自己的原生 UI/系统能力；不为共享界面引入跨平台运行时。target/min SDK、构建插件、HTTP/序列化/存储库及精确版本经 WP-0/E-07 验证后锁定，本版不安装 Android 工具链或声称 Xiaomi 15 已适配。

| 部分 | 拟实施方式与必要错误路径 |
|---|---|
| 组织 | HTTP 合同客户端 → 同步/缓存边界 → ViewModel → Compose 页面；页面消费统一状态，不分别采集上游。数据库和设备身份仍由 NAS 管理 |
| 首次连接 | 管理员在 Web 生成短时一次性码；手机填写 NAS 地址、核实服务身份后兑换独立设备令牌。配对过期/重复兑换/限流/撤销明确反馈；换 NAS 不盲发旧令牌 |
| 权限与网络 | 默认不扫描 LAN；按实际系统/target SDK 核实 LAN 连接与通知权限，拒绝/撤销时保留可读缓存和重试入口。使用系统 TLS 校验，不通过关闭证书验证解决内网证书问题；HTTP 例外不得扩展到公网 |
| 凭据/缓存 | 设备令牌采用平台安全存储候选：Android Keystore 保护加密密钥、应用私有区保存密文；具体库/恢复规则待验证。缓存与偏好分开，凭据不进入普通导出/诊断或可随设备备份复制的明文 |

#### 11.3.3 灾备恢复与换 NAS

受控流程：`isolated → restored_paused → auth_rotated → reconciled → admin_enabled`。阶段失败停留暂停并报告，不能以“容器启动”判恢复完成。

- **先隔离再启动**：关闭/隔离原执行主体，恢复副本默认阻止付费调度与网关管理写入；独立库克隆不共享租约，部署文档必须给出单活检查和解除步骤。不是新增自动 HA。
- **两库与秘密分开**：记录 Relay/LiteLLM 的恢复时间点、迁移版本与加密依赖；仅恢复 Relay 不写覆盖远端。若同时恢复 LiteLLM，核对原生 Key、路由、余额/消费和撤销状态，不能把潜在复活调用 Key 交给旧客户端。
- **先换授权再接受连接**：受控恢复启动前重建授权代际，使备份里的会话、配对码、Mac/Android 凭据和临时操作授权失效；管理员通过独立受控入口确认身份后重配。不能从旧数据库的撤销字段推断恢复后安全，也不声称可检测所有人工复制行为。密码疑似泄露另重置，保护/加密实现由 T-02 冻结。
- **只读核对与费用责任**：核对网关当前状态/日志、游标、任务和预算。已发调用不重放，未知结果不释放费用；当天费用不完整则保持付费暂停，说明人工核对或等待源账本的路径，不能重新发放完整日额度。
- **验证后逐项解除**：原到期正文不可发布，缺失秘密先重配；管理员分别确认采集/付费/管理恢复范围，读回与恢复报告存证。D-10 的 24 小时/60 分钟仍为目标草案，实际备份节奏和恢复测量需记录。对应 FR-O03、AC-44/45/54/16/37；WP-7/8。
