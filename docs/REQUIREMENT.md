- 日期：2026-10-07
- 状态：需求草案，供独立新项目使用；不是实施授权或已完成说明。
- 项目名称：Relay 部署平台（暂定，NEEDS_CONFIRMATION）。
- 交付形态：NAS / Linux Docker 服务端与 macOS 客户端；Web 管理端为建议方案。

## 0. 如何使用本文件

1. 在用户确定的新项目中将本文件保存为 `docs/REQUIREMENT.md`，不要复制到现有 Relay 工程覆盖同名文件。
2. 本文件区分产品需求、建议方案、待确认事项与实现现状。不得将建议方案当成已批准技术栈。
3. 新项目开始前读取自己的 AGENTS.md 和文档，先做兼容性验证，再形成 DESIGN.md。
4. 未完成验证的接口、权限、版本和许可均不能写成“已支持”。
5. 本文不包含真实 Key、密码、账户 ID、个人地址或 NAS 数据文件。
6. 安装依赖、部署容器、迁移数据库、修改旧应用及现有 NAS 服务，需要在相应项目中另行确定范围和授权。

## 1. 背景与产品目标

### 1.1 已确认方向（CONFIRMED）

- 创建独立项目承载 Relay 部署版本，包含 Docker 与 Mac 软件相关交付，不影响当前项目。
- 统一管理多个供应商、中转站及其不同模型，不假定所有渠道提供相同模型。
- 用户配置上游凭据，平台提供面向客户端的调用 Key、网关/路由相关管理能力。
- 提供消费、用量、请求日志、服务探针和模型状态信息。
- 探针覆盖“是否可用”、能力支持和疑似质量回退（用户所称“降智”）。
- 能对接 NAS 已经通过 Docker Compose 部署的 LiteLLM，不要求重新部署或重建网关。
- 优先复用/参考 LiteLLM、Sub2API、CC Switch 等现有项目，不重复造轮子；必要时评估适配或最小修改。
- Mac 软件可以连接服务端；期望配置后自动连接、重连并更新数据。

### 1.2 成功标准（PROPOSED）

用户保留现有 LiteLLM，完成一次接入后，能够：

1. 查看当前可访问模型与渠道，不混淆对外别名和实际上游部署。
2. 查看请求用量、计算费用、可用性和最近数据时间。
3. 管理或导入独立调用 Key，并区分不同客户端与探针流量。
4. 按受控预算进行能力和质量检测，获得附证据的结果。
5. 在 Mac 菜单栏和详情页读取一致、自动更新的数据。
6. 数据库、网络或上游异常时看到明确错误与旧数据时间，而非伪造成功或零消费。

### 1.3 非目标

- 不在首期重写完整 LiteLLM 或建立第二套并行扣费、Key 和预算引擎。
- 不把平台变成公开售卖额度、充值、支付、代理商结算系统。
- 不承诺仅凭探针证明底层模型身份或确认供应商“换模型”。
- 不默认采集所有提示词、回答、工具内容、浏览器 Cookie 或订阅账户会话。
- 不默认接管 NAS 容器、升级现有服务、迁移上游凭据或更改调用路由。
- 不将自动发现视为可信授权，不自动向发现的服务器发送凭据。
- 不默认建设微服务、Kubernetes、集中日志集群或大规模评测集群。

## 2. 当前输入与待核实环境

### 2.1 用户提供的部署情况

用户提供的 Compose 包含：

- Ollama：本地模型运行时，映射端口 11434。
- LiteLLM：配置文件挂载方式，映射端口 4000，镜像标签为 `main-latest`。
- Open WebUI：映射端口 3000，同时配置 LiteLLM 与 Ollama 连接。
- Hermes Agent：配置 LiteLLM 地址及调用凭据。
- workbuddy2api：独立部署，映射端口 7863。
- 共同使用 Docker bridge 网络 `ai-network`。
- Compose 注释涉及 N5105 与 16GB 内存；实际型号、可用资源待核实。

以上是用户提供的配置输入，不是 NAS 在线运行状态或接口验证结果。

### 2.2 NEEDS_CONFIRMATION

- NAS 品牌型号、CPU 架构、系统及 Docker Compose 版本。
- LiteLLM 实际运行版本、镜像摘要、当前许可及可用接口。
- 是否已通过 `.env` 或 LiteLLM 配置连接 PostgreSQL；不能因 Compose 未展示数据库服务就断定没有数据库。
- 请求日志是否保存、保存范围、保留期限及历史完整性。
- Open WebUI 与 Hermes 的实际生效地址、模型和认证配置。
- workbuddy2api 是否已作为 LiteLLM 上游，或目前仍由客户端直连。
- Ollama 聊天/向量请求是否需要纳入统一网关统计。
- 新项目是完整平台源码仓库还是部署编排仓库；建议完整平台源码与部署文件同仓，但尚未决定。

## 3. 产品边界与复用原则

### 3.1 已有网关接入模式（CONFIRMED）

- 支持接入用户自行维护的 LiteLLM。
- 首次连接识别实例、版本、权限与接口能力，展示支持、未支持、无权限、未验证。
- 网关接口根地址与模型调用 Base URL 分开建模，正确处理 `/v1`、反向代理子路径及末尾斜杠。
- 首次验证默认只读、无模型调用；主动推理和写操作必须另外明确启用。
- 不要求通过 Relay 转发所有推理请求；客户端可继续直接调用 LiteLLM。
- 外部网关的启动、升级和数据库生命周期仍由用户维护。

### 3.2 职责分工（PROPOSED）

| 部分 | 建议职责 |
|---|---|
| 既有 LiteLLM | 上游协议适配、模型调用、路由、虚拟 Key、预算、请求记录 |
| Relay 服务端 | 网关适配、数据归一化、监控告警、评测编排、设备 API |
| Relay Mac | 菜单栏与详情展示、设备连接、缓存、通知 |
| Relay Web | 管理连接、模型、Key、探针、告警与部署状态 |

一个主网关拥有调用 Key、预算和请求账本的权威状态；Relay 不维护可与之相互矛盾的第二套状态。

### 3.3 配套网关部署模式（PROPOSED，后续阶段）

- 为尚未部署网关的用户提供经过验证的 Compose 配套方案。
- 不与“连接已有实例”混为一谈，不强制部署第二套 LiteLLM。
- 数据库等依赖按实际功能需要添加，不默认重复创建已有服务。
- 适配器可以逐步扩展，不要求首期同时兼容所有网关。

### 3.4 第三方复用要求（CONFIRMED 原则，具体选型待验证）

- LiteLLM：优先验证其已有 API、配置、日志和健康结果。
- Sub2API：评估账户池/订阅类需求是否适用，不默认串联到所有调用路径。
- CC Switch：参考客户端配置管理或作为连接网关的外部客户端，不默认用作 NAS 后端。
- Promptfoo 等评测工具：候选方案，不预设为已批准依赖。
- 顺序：现有配置/API → 官方扩展机制 → 上游贡献 → 最小 fork。
- 每个拟复用项目记录固定版本、许可证、实际功能覆盖、企业特性限制、维护成本和升级策略。
- 不将“开源”理解为所有功能免费、所有修改均可无条件分发。

## 4. 领域对象与模型支持

### FR-M01：模型目录（CONFIRMED）

- 区分供应商/中转站、账户/凭据、实际部署、对外模型名称。
- 实际部署包含网关实例、稳定标识、协议、端点、上游模型、能力与计价来源。
- 同名模型经不同渠道提供时分别保存状态，不按模型字符串简单合并。
- 显示网关声明支持与实际测试结果；新增模型不自动获得“已验证”标记。
- 仅持有普通调用 Key 时，可只能看到允许访问的别名；实际部署映射无法读取时必须显示未知，不反推或猜测。

### FR-M02：路由与降级（CONFIRMED 目标，管理实现 PROPOSED）

- 对接网关已有模型映射、优先级、负载均衡与故障转移能力。
- 区分同模型切换渠道与切换为不同模型。
- 跨模型降级需要明确配置，并在可获取的请求记录中标识实际模型/部署。
- 不因一次质量失败自动全局下线模型；质量参与路由放在后续阶段。
- 不在流式响应已经交付部分内容后盲目重试或拼接另一渠道输出。

## 5. Key、权限与秘密边界

### FR-K01：凭据隔离（CONFIRMED 目标）

至少区分：

1. 上游模型调用凭据。
2. 上游余额/账单管理凭据。
3. LiteLLM 管理/集成凭据。
4. 客户端模型调用 Key。
5. 探针调用 Key。
6. Relay Mac 设备凭据。
7. Relay 管理员认证。

模型调用 Key 不代表拥有管理接口或账单读取权限；Mac 监控凭据不代表模型调用权限。

### FR-K02：调用 Key 管理（CONFIRMED 目标，分阶段交付）

- 优先使用网关原生虚拟 Key，支持名称、允许模型、预算、有效期及撤销等实际可用能力。
- 无权限或版本不支持时，降级为查看/导入已有 Key；不得假装创建成功。
- 建议分别为 Open WebUI、Hermes、其他客户端与探针创建 Key，方便归属和预算隔离。
- Key 创建结果只在必要时显示一次；日志、导出、URL、埋点不得包含秘密值。
- 写操作需要管理员授权、操作结果和审计记录；失败不得留下伪成功状态。
- 分发调用 Key 必须是明确管理操作，不通过监控设备配对自动发放。

### FR-K03：秘密存储（NEEDS_CONFIRMATION）

- 新服务端的秘密保护方案需独立设计：访问控制、存储保护、备份、轮换、丢失恢复与日志脱敏。
- 现有 Mac 项目“不使用 Keychain”的决定不能自动推广为 NAS 秘密存储方案。
- 文件权限、环境变量或 Compose secrets 文件挂载不得描述成加密保险库。
- 不把包含管理 Key 的通用 `.env` 无差别注入所有客户端容器。
- 不自动上传现有 Mac 的上游凭据到 NAS；任何迁移需另行确认。

## 6. 统计、日志与账本

### FR-D01：请求范围与统计（CONFIRMED）

- 读取网关已记录的请求、模型、Key 归属、Token、计算费用、时间及实际可得的状态/延迟。
- 支持按日/月、模型、Key、实例筛选；未支持维度明确标识，不用空值伪造支持。
- LiteLLM 统计仅覆盖经过该网关且实际被记录的调用，不代表整个 NAS 或全部供应商账单。
- 直连 Ollama、workbuddy2api、供应商的流量不自动计入。
- 区分用户调用、探针/评测调用及无法分类的调用；不能保证上游内部健康检查都带独立 Key，无法分类时不得冒充用户消费。

### FR-D02：价格与余额（CONFIRMED）

- 网关计算费用、上游已确认账单和上游账户余额分别展示，不叠加为“总消费”。
- 支持不同渠道价格、原生币种/积分、折扣及来源记录。
- 金额区分已确认、估算、未知；未知价格不能作为免费或 0 费用。
- Token 数量缺失与真实 0 分开；缓存/推理等分类仅在来源提供时展示。
- 汇率保留来源和有效时间；不可比较、过期或不完整时不进行误导性汇总。
- 余额/账单连接器属于独立能力，调用 Key 不保证能读取余额。

### FR-D03：采集一致性（PROPOSED 必要约束）

- 正确处理分页、窗口、时区、接口截断和保留期；展示数据覆盖范围与完整性。
- 以稳定请求标识或已验证的去重规则实现幂等采集，不只靠时间戳去重。
- 增量游标与对应数据需一致提交；失败不能推进游标而丢失记录。
- 请求、重试尝试和逻辑调用需区分；准确呈现无法确认的计数口径。
- 可重叠回查处理延迟入库；源日志缺失时不能声称恢复出完整历史。
- 服务端为远程模式统计事实源，Mac 仅缓存；禁止 NAS、Mac 与 iCloud 并行写同一账本。

### FR-D04：隐私与保留（PROPOSED）

- 默认仅采集必要元数据，不采集完整提示词、回答、工具内容和附件。
- 完整内容调试需显式启用，设置访问权限、保留期和删除方式。
- 网关日志、Relay 日志、评测结果和客户端历史分别审查，不能因一个脱敏开关就声明全链路安全。
- 原始日志与聚合历史的保留期独立；数据库磁盘增长需可监控。
- 导出和备份不得默认包含秘密或内容正文。

## 7. 探针与质量评测

### FR-P01：三种状态独立展示（CONFIRMED）

1. 可用性：认证、模型访问、请求/流式完成、超时、限流、延迟。
2. 能力：流式、工具调用、结构化输出、视觉、上下文及关键参数。
3. 质量：固定任务上的表现与基线变化。

状态包含通过、失败、不支持、未测试、过期和证据不足。网关进程正常不等于模型可用；请求成功不等于能力或质量合格。

### FR-P02：基础探针复用（CONFIRMED）

- 优先读取既有 LiteLLM 健康结果，区分网关就绪和实际模型调用。
- 页面刷新不触发全模型主动推理。
- 缓存结果必须带检测时间和过期状态，不能无限显示绿色。
- 没有配置主动探针时不自动启用付费请求。

### FR-P03：主动能力与质量探针（CONFIRMED 目标，具体工具 PROPOSED）

- 测试集、提示词、参数、评分规则及基线版本化。
- 固定实际部署；禁用会掩盖目标失败的 fallback。无法固定时只能报告路由组结果，不能声称验证了具体渠道。
- 控制输出预算、推理参数、缓存及采样，重复检测后判断趋势。
- 优先客观断言、结构验证和受控单元测试；模型裁判作为补充并标注其局限。
- 排除超时、截断、预算不足、参数被移除、路由变化造成的误判。
- 可比较经网关与直接上游结果，但直接验证需要另行授权上游凭据和费用。
- “疑似质量回退”附样本量、版本、失败示例和对比基线，不证明模型身份。
- 使用合成测试数据；若执行模型生成代码，必须隔离网络、文件、秘密和资源，不在 NAS 宿主机直接执行。

### FR-P04：费用与资源控制（PROPOSED）

- 探针有可选模型、频率、并发、输出限制、每日额度、手动停止和预算耗尽处理。
- 未知单价不能绕过保护，应通过请求次数/Token 上限或明确审批约束。
- 付费探针开启前说明成本和范围；质量评测不可在版本升级后自动扩大。
- 本地 Ollama 探针单独安排，避免周期唤醒挤占 NAS 资源。
- 网关内置健康检查与 Relay 调度不可无控制重复执行。

## 8. 告警与状态

### FR-A01（PROPOSED）

- 支持持续不可用、认证失效、日志采集失败、预算接近阈值、疑似质量回退和恢复事件。
- 有防抖、连续失败阈值、冷却和恢复通知，避免单次失败告警风暴。
- 告警附实例、部署/模型、原因、证据时间；不附 Key 或完整用户内容。
- 首期建议 Web/Mac 内通知；邮件、Webhook 等渠道后续确定。
- 质量告警首期仅建议人工复查，不触发自动全局封禁。

## 9. Mac 客户端

### FR-C01：连接与自动重连（CONFIRMED）

- 首次配置服务地址并完成授权，保存设备连接信息。
- 重启、网络恢复后自动重连，采用退避、取消和错误隔离。
- 断线展示最后成功数据、更新时间和断线状态；不能冒充实时数据。
- 地址发现为可选功能；不自动信任新实例或发送原有凭据。
- 服务端不可达时不静默切回直接访问供应商，避免重复采集和凭据泄露。
- 默认设备只读，可撤销；设备管理与服务器证书信任方案待设计。

### FR-C02：刷新一致性（CONFIRMED）

- 首页、账户/网关详情、模型详情随同一数据版本更新，详情页不保留打开时的静态副本。
- 临时读取失败保留旧数据与窗口，并显示失败信息；仅确认删除后展示删除状态或退出。
- 隐藏列表项不等于删除，隐藏/停用对象的已打开详情仍可展示其保留状态。
- 跨日消费及时失效，不能把昨日值继续显示成今日消费。
- 单个网关或上游失败不覆盖其他正常数据。

### FR-C03：交付边界（NEEDS_CONFIRMATION）

- Mac 最低系统版本、CPU 支持、签名、公证、更新方式。
- 复用现有 Relay 原生 UI/逻辑的范围、授权和独立应用身份。
- 是否保留本地独立运行模式；不默认同时维护两套统计模式。
- 首期只显示监控，还是包含 Key 管理与客户端配置导出。
- 自动配置 CC Switch 等客户端需单独明确目标与授权，不覆盖用户现有设置。

## 10. Web 与 Docker 交付

### FR-W01：Web 管理端（PROPOSED）

建议提供实例连接、模型/部署目录、Key 管理、统计、探针计划/结果、告警及设备管理。
具体页面与 UI 未确认，不从本草案推定已批准布局。

### FR-O01：部署与升级（CONFIRMED 形态，以下验收 PROPOSED）

- 提供 Docker 镜像、Compose 示例、配置模板、运维说明和 Mac 安装交付。
- 支持连接已有 `ai-network`；接入已有网络时不得意外重建或删除用户网络。
- Docker 内使用可解析的服务名，Mac 使用 NAS 可访问地址，不混淆两类地址。
- 数据持久化、健康检查、重启恢复、日志滚动、磁盘管理需可验证。
- 数据库默认不发布宿主机端口；对外端口、绑定地址和远程访问策略明确。
- 使用已验证版本/摘要，不依赖浮动 `latest` 宣称兼容。
- 默认先支持实测的 NAS 架构；其他架构未构建和测试不得声称支持。
- 升级前备份，说明数据库迁移、版本兼容和回滚限制；不能假定降级镜像即可回滚数据库。
- 不提供删除持久卷作为排错常规步骤，不执行无授权清理。

### FR-O02：安全与性能（PROPOSED）

- 跨不可信网络通信要求 TLS；局域网明文例外需用户明知，不默认暴露管理 API 到公网。
- 上游/探针地址需 SSRF 防护；Ollama 等私有端点只能经管理员明确许可，不全局关闭防护。
- 限制请求体、查询窗口、日志导出、任务并发和评测资源。
- 基于实际 NAS 测量内存、CPU、磁盘及并发，不承诺 N5105 能承担高并发质量评测。
- 首期避免不必要的 Redis、Prometheus、Grafana 等附加依赖；有明确收益再加入。

## 11. 建议实施路线（PROPOSED，尚未批准排期）

| 阶段 | 范围 | 退出条件 |
|---|---|---|
| M0 兼容验证 | 现有 LiteLLM 版本、权限、数据库、接口及真实调用路径 | 形成支持矩阵和最小测试记录；默认不调用付费模型 |
| M1 只读闭环 | 实例接入、模型目录、日志统计、现有健康结果、Mac 连接 | 能稳定展示真实数据，失败保留缓存，详情同步刷新 |
| M2 管理与能力探针 | 原生虚拟 Key 管理、必要路由管理、预算与能力测试 | 权限隔离、费用限制、撤销与异常场景通过 |
| M3 质量评测 | 基线、版本化测试集、重复采样、证据与告警 | 能区分可用性失败和疑似质量回退，不声称模型鉴真 |
| M4 扩展 | 配套 Compose、更多适配器、客户端配置、受控质量路由 | 按新增需求分别验收，不倒灌进首期范围 |

Web 管理界面的具体交付阶段随管理需求确认；M1 不自动包含所有管理功能。

## 12. 验收矩阵（PROPOSED）

| 编号 | 场景 | 预期 |
|---|---|---|
| AC-01 | 接入既有 LiteLLM | 不重建实例、不改上游，显示版本/权限/支持矩阵 |
| AC-02 | 无数据库、日志未启用或无权限 | 明确原因和配置建议，不把缺失统计显示为 0 |
| AC-03 | 两个渠道同名模型 | 部署状态独立；无权读取映射时显示未知 |
| AC-04 | 已知请求与日志查询 | 模型、Key、Token、时间与来源可核对，费用标记来源 |
| AC-05 | 直连 Ollama / workbuddy2api | 不混入 LiteLLM 总量，界面显示统计范围 |
| AC-06 | 分页/重复回查/延迟入库 | 不漏已覆盖数据、不重复计数，失败不推进游标 |
| AC-07 | 创建/撤销独立调用 Key | 权限校验；客户端分开归属；不泄露管理 Key |
| AC-08 | 模型主动探针 | 用户先启用；预算/频率有效；页面刷新不重复触发 |
| AC-09 | fallback 掩盖失败 | 固定部署测试或标为组级，不误报渠道可用 |
| AC-10 | 工具/结构化输出测试 | 不把 200 响应当功能通过，验证实际结果 |
| AC-11 | 输出截断/超时/参数丢弃 | 单独归因，不直接认定降智 |
| AC-12 | 疑似质量回退 | 有基线、版本、样本与证据；默认仅告警 |
| AC-13 | Mac 首次配对、重启和恢复网络 | 自动重连；凭据撤销后失效；不信任任意新实例 |
| AC-14 | 详情打开时服务端更新 | 首页/详情更新到新版本；无需关闭再打开 |
| AC-15 | 读取失败/跨日/隐藏停用 | 保留旧窗口且标过期；今日值失效；不误判删除 |
| AC-16 | 容器重启/升级/备份恢复 | 持久数据保留；迁移和回滚按文档验证 |
| AC-17 | 日志/导出/错误信息 | 不含 Key；默认不含提示词和回答正文 |
| AC-18 | SSRF 与评测执行 | 未授权内部目标被拒绝；生成代码隔离执行 |

付费真实调用仅在用户明确批准测试范围后执行。Mock/离线测试与真实接口测试分别报告，不能互相替代。
